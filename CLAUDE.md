# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Fizzygum is

A CoffeeScript GUI framework — a "web operating system" (windows, desktop, drag-and-drop, live in-system editing tools) rendered on a single HTML5 `<canvas>`.

## Build, run, watch

Prerequisites are installed **globally, not via `npm`**: `coffee` (`npm i -g coffeescript`), `terser`, and `fswatch` (watch script only), on Node 20 or later (`buildSystem/lib/profile.js` checks every JSON string with `String#isWellFormed`). `npm test` runs `./fg presuite` — see Testing.

- **Build:** `./build_it_please.sh` → output goes to `../Fizzygum-builds/latest`.
  - **A build FLAVOUR is a PROFILE, not a flag:** `--profile <name>` selects `buildSystem/profiles/<name>.json`, and a plain invocation builds `dev`. ⛔ `--homepage` and `--notests` are DELETED (arc 5) and now fail loudly; the shipped profiles are:
    - `dev` (default) — every part, compiled in the browser, all three entry pages.
    - `dev-precompiled` — `dev`, but booting from a PRE-COMPILED image instead of compiling in the browser: same parts, `sources: "lazy"`, and `index.html` ONLY. ⚠ The single entry page is FORCED, not a simplification — an image is harvested by booting ONE page, and `index-sw.html`/`worldWithSystemTestHarness.html` preset `FIZZYGUM_EAGER_ALL_PARTS`, so they would ingest sources for classes that image never defined (`Cannot set properties of undefined (setting class)`, measured twice). ⇒ the suite does NOT run on this tree, and does not need to: `dev` stays the default. This is for the human who opens `index.html` and drives the world by hand.
    - `homepage` — the production artifact: pre-compiled, `sources: "lazy"`, `index.html` only, and thirteen parts — `core` plus TWELVE that are all **LAZY**: `app-kit` (the shared base layer the app parts derive from) / `meta-tools` / `maps` / `plots` / `spreadsheet` / `authoring` / `examples-icons` and the five one-class `example-*` doors of the Examples folder.
    - `dev-notests` — `dev` minus the `harness` part (which also owns `src/macros`) and the harness page: `lib/profile.js` refuses `worldWithSystemTestHarness.html` without the part.
    - `lean` — the appliance artifact: `core` only, pre-compiled, and `sources: "none"` — no `js/coffeescript-sources/` at all. ⚠ Because `sources: "none"` **forbids shipping a lazy part at all** (a lazy part's source *is* its code — the image is harvested by booting `index.html`, where lazy parts do not load), the appliance necessarily has none of the **Makers** — no Docs, Sheets, Slides, Dashboards, Draw, Patch programming, Generic panel or Super toolbar — and correctly no desktop icons for them: `createDesktop` asks `world.parts.canEverProvideClass` before drawing each icon, so a profile that cannot produce an app simply draws none — an icon whose click could only reject is worse than no icon. ⚠ It also cannot inspect or rewrite itself, and a loaded snapshot carrying class-level source edits still loads, and its one `inform` says how many of them this build cannot re-apply (per-widget `{"$src"}` edits still work — those need only the compiler, which every profile ships).
  - `--noSyntaxCheck` — skip the build-time CoffeeScript syntax gate (see Testing).
- **✅ Test a change — PREFERRED / DEFAULT:** `./fg presuite` — `fg`, this repo's workflow wrapper (`Fizzygum/fg`; it runs from any cwd, and the umbrella's `Fizzygum-all/fg` is a shim that execs it), builds, then runs the whole SystemTest suite **headless, in parallel shards, at `speed=fastest`, dpr 1** beside the paint audit and a dpr-2 rider (~3–4 min on a many-core box). `./fg gauntlet` is the full commit-point check, and `./fg` alone prints every subcommand. This is the standard way to verify a behaviour change; don't watch the suite in a browser (~15 min) or run tests one-by-one unless debugging a single test. One-time setup: `cd ../Fizzygum-tests && npm i` (Puppeteer).
- **Build + boot-smoke gate:** `./build_and_smoke.sh` builds (incl. the syntax gate) then headless-boots every entry page the profile ships (`index.html` native, `index-sw.html` SWCanvas, `worldWithSystemTestHarness.html` SWCanvas + the test harness), failing on any console error — a lighter boot-only check (use when a full suite run is overkill).
- **Watch + rebuild on save:** `./build_as_soon_as_anything_changes.sh` (`fswatch` over `src/`; the syntax gate runs on every save).
- **Run:** open `../Fizzygum-builds/latest/index.html` in a browser. It loads over `file://`; no dev server needed. (`index-sw.html` is the same world rendered by the SWCanvas software backend; `worldWithSystemTestHarness.html` is that plus the test harness.)
- **Find duplicated code:** `./find_duplicated_code.sh` — jscpd (devDependency) over `src/**/*.coffee`, no compile step (CoffeeScript is tokenized natively); console/JSON/markdown/HTML reports plus an LLM-handoff clone-pair list land in `duplication-report/` (gitignored). Tuning + gotchas (jscpd silently skips >1000-line files at its defaults — config raises the caps): `docs/tooling/duplicated-code-detection.md`.
- **Find SIMILAR (renamed/structural) code:** `./find_similar_code.sh` — jsinspect AST matching over a CoffeeScript-1-compiled ES5 mirror (`buildSystem/coffee-to-js-mirror.js`); catches the renamed/near-miss clones jscpd's exact-token scan can't. ⚠ its reports carry compiled-JS line numbers — navigate by file + `@method` name. Both scanners take `--tests` to scan the sibling `Fizzygum-tests` repo (harness + node scripts) instead. The recurring **re-audit → triage-ledger → LLM-session cycle** (incl. the `duplication-report/triage-report.md` ledger convention and its end-of-arc snapshot into `docs/archive/`) is documented in the same docs file: `docs/tooling/duplicated-code-detection.md`.

The build must run from a repo whose parent directory is named `Fizzygum-all`, and aborts otherwise. The layout it hard-codes `../` paths into:
```
Fizzygum-all/
  Fizzygum/          ← this repo (source only)
  Fizzygum-builds/   ← build output (generated; never hand-edit — created for you if absent)
  Fizzygum-tests/    ← SystemTests + Automator source (separate repo, REQUIRED: the build aborts up front
                       without it — the harness part's sources, the precompiled image's driver and the
                       build's gates live there, and every gate run on its own refuses without it too)
```
(`Fizzygum-website/` appears in the build's own abort message and in older docs, but nothing reads it — it is not checked out here and is not needed to build or test.)

## Architecture (the non-obvious parts)

- **How a build is assembled and selected — the partition, the profiles, and what each profile DERIVES rather than declares — is in [`docs/architecture/build-and-packaging.md`](docs/architecture/build-and-packaging.md).** Read it before touching `parts.json`, `buildSystem/profiles/*.json`, `lib/profile.js`, `build.js` or `build_it_please.sh`. Its RUNTIME half — how a page boots (the two paths: compile-at-boot vs the pre-compiled image), when the reflective layer arrives, and how `world.parts` (`PartsRegistry`) brings a LAZY part in behind an already-running world — is §2/§5 of that same doc, illustrated by [`docs/explainers/boot-and-lazy-parts.html`](docs/explainers/boot-and-lazy-parts.html). Read that before touching `src/boot/*`, `PartsRegistry`, or any door that awaits a part.
- **Subsystem references live in `docs/architecture/`** — present-tense, verified-against-src: the layout/settle engine ([`docs/architecture/layout.md`](docs/architecture/layout.md): the world cycle, settle tiers, ordered down-walk, constraint-box sizing, the layout-spec FAMILY (§4.2 — one spec object per attachment, knob-vs-record lifecycle), claimsSpace, the standing zero-invariants, the new-layout rulebook), the affine transform islands ([`docs/architecture/transforms.md`](docs/architecture/transforms.md): TransformFrameWdgt islands, TransformSpec, the two-vocabulary law, the lens declarations, pinned anchors, plane-mapped input, the island buffer cache), and the scrolling-container family ([`docs/architecture/viewports-and-planes.md`](docs/architecture/viewports-and-planes.md): `ViewportWdgt` the chrome composite, the plane ROLE + `ScrolledPaneWdgt`, the runtime `scrollPolicy 'auto'|'never'` crop⇄scroll flip, the scrolled-content contract, and why `PanelWdgt` is purely the SURFACE class). Read those before touching any of the three subsystems.
- **The rendering backend is a BUILD-TIME property of the entry page.** `buildSystem/build.js` writes every entry page from the single source `src/index.html`, substituting a `window.FIZZYGUM_USE_SWCANVAS` preset plus the matching boot-bundle tag for the `<!--FIZZYGUM_BOOT_SCRIPTS-->` placeholder (the `ENTRY_PAGES` table of `buildSystem/lib/profile.js`): `index.html` → native + `js/fizzygum-boot-native-min.js`; `worldWithSystemTestHarness.html` and `index-sw.html` → SWCanvas + `js/fizzygum-boot-sw-min.js`. There is **no runtime `?sw=` switch**: a page missing the preset `console.error`s at boot. To add an entry page, add a row to `ENTRY_PAGES`.
- **Source-as-text + in-browser compilation.** `buildSystem/build.js` does *not* compile `src/` classes. It wraps each class's CoffeeScript source into a JS string literal and hands it to the **`SourceVault`** — `SourceVault.store("<Name>", "<text>", "<part>")`, grouped into a few `sources_batch_*.js` files per part; the browser compiles them at boot with the bundled CoffeeScript compiler. ⛔ The predecessor — one `window.<Name>_coffeSource` global per class, discovered by suffix-scanning `Object.keys(window)` — is **RETIRED (arc 4)** and gated (`buildSystem/check-source-vault.js`): do not reintroduce either the naming convention or a window scan. ⚠ **That source text is a build INPUT to any precompiled artifact**, even one whose profile says `sources: "none"` — the driver harvests the image by booting the tree in compile-at-boot mode, so the text (and `js/src/dependencies-finding-min.js`) must exist during the build and is dropped after the driver runs, never skipped earlier.
- **No imports / no module system.** Zero `require`/`import`; every class is a global. Load order is auto-discovered by `src/boot/dependencies-finding.coffee`, which *regex-scans source text* for `extends X` and `new X`. To reference another class just name it — but use those literal forms so the dependency finder sees the edge. To turn a NAME that is DATA (a file's record class, an `app:` key, a launcher's app, a part's door) into a class, ask boot's `classNamed name` (`src/boot/globalFunctions.coffee`: an OWN data property of `window` carrying the class marker), never `window[name]` — a plain lookup also answers inherited properties (`constructor`, `__proto__`), runs accessors (`location`) and finds native globals (`Object`); `allClassFunctions()` enumerates exactly the names `classNamed` answers.
- Widgets form a tree, painted recursively; a Widget with no owner is never drawn.
- **Writing a widget class — the house rules are in [`docs/architecture/widget-authoring-guidelines.md`](docs/architecture/widget-authoring-guidelines.md)**: one section per decision a widget author faces (constructor shape and the `@param` trap, the `_buildAndConnectChildren` pair, class-level field declaration, the `createAppearance` factory, when `_reLayoutChildren` is yours to define, settle tiers, self-invalidation, input, menus, pin setters, stepping, teardown, type tests vs capability queries), each with the gate that enforces it, plus a checklist and a skeleton. Read it before adding a `*Wdgt`.
- A widget invalidates only ITSELF — `@_changed()` (just this widget) / `@_fullChanged()` (it + its subtree), both PRIVATE: never call them on another widget (widget-citizenship point 2, gated by `check-invalidation-receivers.js`); cross-object repaint goes through intent-named public methods on the receiver (e.g. `world.noteWallpaperChanged()`, `world.caret.noteTextChanged()`) — there is no general-purpose public repaint verb.
- **Dataflow / spreadsheet engine — a drain station of the world cycle.** `WorldWdgt.doOneCycle` runs **four drain stations** (`docs/architecture/layout.md`): `recalculateDataflow` (settles VALUES) runs BETWEEN `runChildrensStepFunction` and `recalculateLayouts` (settles GEOMETRY), and the coupling is one-way — dataflow may dirty layout, never the reverse. A change marks nodes **stale**; values are **pulled** at recompute time (notifications carry no values); the forward/reverse edge index is derived and never serialized. Design: [`docs/specs/dataflow-engine-spec.md`](docs/specs/dataflow-engine-spec.md); depth: [`src/dataflow/CLAUDE.md`](src/dataflow/CLAUDE.md) + [`src/spreadsheet/CLAUDE.md`](src/spreadsheet/CLAUDE.md); measured convergence (typical 1 pass): [`docs/measurements/dataflow-measurements.md`](docs/measurements/dataflow-measurements.md).
- **Window drag-embed (dwell-to-arm).** Float-dragging a *window* over a receptive container embeds it only after a ~450ms **dwell** (held still within 7px; `ActivePointerWdgt` state machine — `dwellToArmMs`), so a window never nests by accident; an unarmed release lands it on the desktop, and dragging a nested window out ejects it. Design + as-built deviations: [`docs/specs/drag-embed-interaction-spec.md`](docs/specs/drag-embed-interaction-spec.md); arc history: [`docs/archive/drag-embed-implementation-plan.md`](docs/archive/drag-embed-implementation-plan.md) and [`docs/plans/frame-lifetime-and-docking-plan.md`](docs/plans/frame-lifetime-and-docking-plan.md) (the dock bands).
- **There are no mixins**: every behaviour once injected by one lives in an ordinary home (`docs/archive/mixin-removal-plan.md`). **All serialization / deserialization / duplication internals — format, traversal contract, per-class protocol, `file://` I/O — are documented in one place: [`docs/architecture/serialization-duplication-reference.md`](docs/architecture/serialization-duplication-reference.md).** A behaviour shared across unrelated branches finds an ordinary home: a base class, an appearance, a plain collaborator class (the `MacroToolkit` pattern — `world.macroToolkit`, in `src/macros/`), or a question asked of the object that owns the fact (a pointer look asks the hand at paint); the rule for choosing among them, and what moving a member up to a base class changes: [`docs/architecture/widget-authoring-guidelines.md`](docs/architecture/widget-authoring-guidelines.md) §16 (the old mechanism's history: [`docs/archive/mixins.md`](docs/archive/mixins.md)).

## Testing

**The build runs its project-specific STATIC GATES — the rows of one table, `buildSystem/gates.js`, run in order by `buildSystem/run-gates.js` — and their complete index — what each one checks, what it provably CANNOT see, and how to sanction an exception — is [`docs/architecture/lint-and-static-checks.md`](docs/architecture/lint-and-static-checks.md).** The first of them runs every checker's own self-test (`*-selftest.js`, found by name, never listed), so a gate whose proof broke stops the build before its verdict is read — and it refuses a GATE (any script the build, `build_and_smoke.sh` or an `fg` leg launches, unless its header states `not-a-gate: <reason>`) that names no rules (`buildSystem/lib/gate-rules.js`) or that no proof launches: every rule of every gate is planted and seen failing by its own line, at the build for the static gates and in the gauntlet's `selftests` leg for the legs (the index's §3, "every gate's every RULE is proven to BITE"). Read the index before concluding a class of bug is uncaught, and before writing a new gate. ⚠ Every gate has a stated blind spot, and a RUNTIME twin exists beside a static gate whenever that blind spot is "the name resolves but the thing behind it is wrong": `check-menu-actions.js` catches a menu-dispatched parameter that is UNREAD and structurally cannot catch one read as the wrong THING or one MISSING altogether, so `fg menusweep` clicks every menu item (and proves every row's `opensSubmenu` flag against what the click opened); and no text scan can decide whether an advertised pin is serviceable — a `PinSpec` names its setter by STRING and `pins()` is COMPOSED, so a subclass can NARROW it — so `fg pinsweep` resolves every advertised pin and drives every `announces` fixture.

Two fast automated checks complement the (manual/browser) SystemTests:
- **Build-time syntax gate** (`buildSystem/check-coffee-syntax.js`, run automatically by `build_it_please.sh`): since the class sources ship as text and compile in-browser, this is what catches CoffeeScript *parse* errors at build time. Its header has the rest.
- **Headless boot smoke** (`../Fizzygum-tests/scripts/smoke-boot-headless.js`, via `./build_and_smoke.sh` or `cd ../Fizzygum-tests && npm run smoke`): headless-boots every shipped entry page (`index.html` native, `index-sw.html` SWCanvas, and the harness page — where it also asserts the harness is really there: the world's automator built and a non-empty tests manifest) and fails on any console/page error — catching the load-order/runtime faults the syntax gate cannot, including a harness-only boot fault the two product pages cannot see. Its header has the rest.

- **ONE world teardown, two callers, TWO obligations.** `WorldWdgt._teardownWorldStructureNoSettle` is a **shipping** core, and a line added to it belongs to one of two contracts with different lifetimes, failure modes and gates. **(A)** *after `fullDestroyChildren()`, the world holds no reference to anything just destroyed, and no bookkeeping that assumed it still exists* — the off-tree containers (destroyed WHOLE: the bin and shelf are snapshot roots neither caller keeps, so emptying them would leak the shells on every load), the widget the hand is carrying, the app-window registry (`appWindows`), `errorConsole`/`lastEditedText`, the tooltip/pop-up/handle/highlight collections, the damage-suppression depth, the one-shot `infoDoc_*` flags; ~25 of its ~28 actions, observable only where the world SURVIVES, so `loadWorldSnapshot` is the enforcer and `world.teardownHygiene.*` the measurement. **(B)** *page-lifetime state lets go of what was just destroyed* — a class static (`WorldWdgt.timeOfEventBeingProcessed`), a class-level timer registry (`ToolTipWdgt.ongoingTimeouts`) and a module-level store (the SWCanvas cold-glyph array): these outlive every world the page builds, so **discarding a world does not touch them** and they are owed on BOTH paths, enforced by the object-lifetime tier (`WORLD_INVENTORY_*`, `fg vmtruth`). ⚠ The split is measured, not argued, and it is easy to get backwards: removing an (A) line leaves a reset sequence GREEN and fails only the snapshot rig, while removing a (B) line fails the RESET path with `WORLD_INVENTORY_DRIFT` even though that world is dissolved a phase later. Restoring what the world should LOOK like afterwards is the **caller's** job, and since Arc C the two callers answer that very differently: `resetWorld` restores nothing, it **CONSTRUCTS** — `_dissolveWorldNoSettle` kills the old world, then `new WorldWdgt` + `finishWorldSetup` build a fresh one and `window.world` is swapped — so a pristine world is pristine BY CONSTRUCTION rather than by a cleanup pass that remembered everything; `loadWorldSnapshot` keeps its world and restores the file's contents onto it. ⛔ The harness verb `_resetWorldNoSettle`, which used to own the pristine-LOOK half, is **GONE** (it also SHADOWED the shipping `resetWorld`); the harness now takes two SEATS at the shipping reset instead — `_beforeBeingDissolved` (last rites on the OLD world) and `_afterWorldResetNoSettle` (arming instruments on the NEW one). ⚠ The core still matters exactly as much: `loadWorldSnapshot` is its other caller and gets NO reconstruction, so a reference the core forgets is still a live product bug there. They were hand-synchronised twins until 2026-07-29 and had drifted twice in two days in opposite directions, leaking real product bugs (a DESTROYED `errorConsole` swallows every later paint error in the session; the additive-only `infoDocFlags` restore can never clear a flag the file lacks). ⚠ Anything you add to a teardown belongs in the core unless it restores appearance. Gates: ⚠ the `WORLD_CONSTRUCTION_DRIFT` ratchet (below) does NOT cover the core through `resetWorld` — a reference the core forgets there is forgotten on a world that is about to die, so it cannot reach the fresh world's fingerprint.
- **Construction-determinism ratchet** (`WORLD_CONSTRUCTION_DRIFT`; it lives in `../Fizzygum-tests/Automator-and-test-harness-src/WorldTestSupport.coffee`, whose comments have the rest, and runs at every test's reset). The guard fingerprints the first RECONSTRUCTED world's own mutable state — reading every field through the prototype chain, as an effective VALUE, never as "does the world own it" — and re-checks every later world against that **page-scoped** baseline, `console.error`ing `WORLD_CONSTRUCTION_DRIFT` on any disagreement; it is **wired into the headless runners' fail-gate** like `NON_INTEGER_GEOMETRY`. If it fires: find what the constructor or `finishWorldSetup` reads, or name the field in `WorldWdgt._worldStateAuditExemptions` **with its reason** (monotonic counters, deliberate measurement switches, and clock readings taken at construction are legitimate exceptions — `lastTime` is the one reconstruction itself created; anything that can reach a render is not). Audit + full inventory: [`docs/archive/resetworld-teardown-completeness-audit-plan.md`](docs/archive/resetworld-teardown-completeness-audit-plan.md); bug class: `../Fizzygum-tests/DETERMINISM.md` §2d.

Behavioural tests are **SystemTests**: each one drives the running world from a high-level **macro** (a generator that asks the live world where things are and synthesises real input events), then compares canvas screenshots pixel-by-pixel against reference images.
- **Author:** write the test directly as a macro — the framework-side helper toolkit lives in **`src/macros/`** (engine `Macro.coffee` + `MacroToolkit.coffee`, reached as `world.macroToolkit`) and is documented in **`src/macros/CLAUDE.md`**; see also the `/author-macro-test` skill in `Fizzygum-tests`.
- **✅ Run the whole suite — PREFERRED / DEFAULT:** `./fg presuite` (build + suite + paint audit + dpr-2 rider), or against an existing build `cd ../Fizzygum-tests && npm test` (= `scripts/run-all-headless.js`). `npm run test:all` is the single-process variant. The suite can also run **headless under Safari/WebKit** (Chrome stays default) as a cross-engine determinism check — `--browser=webkit` / `npm run test:webkit`, reusing the same references; see `../Fizzygum-tests/CLAUDE.md`.
- **Run one (debugging a single test):** open the built `worldWithSystemTestHarness.html`, then `world.automator.loader.loadAndRunSingleTestFromName('SystemTest_name')`; or headless `node scripts/run-macro-test-headless.js SystemTest_<name>`.
- **Determinism (the suite asserts byte-exact pixels — keep it deterministic):** render/layout/input code must be a pure function of the **event stream** and **final geometry**, never of wall-clock timers (`setTimeout`/`Date.now`), frame/cycle counts, or intermediate layout passes — those diverge at **dpr 2 under parallel load** (heavy cycles starve timers and drain multiple events per frame). The contract, the recurring bug-class with worked case law, and the diagnosis playbook (deterministic heavy-cycle reproduction, pixel-delta forensics, disable-the-mechanism proof) are in **`../Fizzygum-tests/DETERMINISM.md`** — read it before touching the rendering loop, `_reLayout`, or `ActivePointerWdgt` input recognition.

## Conventions & gotchas

- **`docs/` is bucketed by what a file IS — keep the split honest** (map + full filing rules: `docs/README.md`): `architecture/` how it works NOW · `specs/` behaviour contracts · `plans/` ACTIVE arcs only · `archive/` closed/falsified/parked plans, verbatim + status-stamped, indexed in `archive/INDEX.md` · `measurements/` dated snapshots · `tooling/` dev-tool how-tos. The standing loop: new arc → `plans/`; arc closes → `git mv` to `archive/` + stamp + INDEX line; durable residue → the subsystem's `architecture/` doc **in the same arc**; every open/deferred item gets a `docs/BACKLOG.md` line pointing at its owning plan section.
- **This file has a byte CEILING**: `buildSystem/check-doc-narration.js` (the gauntlet's `refs` leg) fails when it grows past the size `buildSystem/check-doc-narration-baseline.json` records. It keeps routing, the commands, the rules and one line per rig; mechanism, history, measurements and case law go to the rig's header or the architecture doc that owns them (`docs/architecture/lint-and-static-checks.md` §3b-docs).
- **One class per file; filename must equal the class name** (`Widget.coffee` ↔ `class Widget`).
- **`Wdgt` is the widget suffix, and it is now universal** — the `*Morph` legacy inherited from Morphic.js is fully migrated: zero `*Morph` classes remain, and the handful of surviving mentions are provenance comments plus `Widget`'s defensive `/(Wdgt|Morph)$/` strip. New widgets are `*Wdgt` from the start. ⚠ The lesson of that migration outlives it and applies to ANY class rename: a rename here is *not* always pixel-free — menu/hierarchy labels strip `Wdgt`, so renaming a class whose colloquial name is DRAWN (menu items, for instance) shifts that label and forces SystemTest screenshot recapture; verify per class, and do a family in ONE verifiable batch, since each rename is a whole-tree identifier+file+serialization sweep.
- **`undefined` is the codebase's ONE absence value** — spelled the way the language spells it. ⛔ The `nil = undefined` global is **RETIRED** and gated at zero by the `nil-literal` stink — do not reintroduce it or any other alias for a language primitive.
- **⚠ A CoffeeScript `@param` in a constructor signature ASSIGNS THE FIELD UNCONDITIONALLY — so it SHADOWS the class-level default. This is true WITH OR WITHOUT a default on the parameter.** `constructor: (@backgroundTransparency) ->` compiles to a plain `this.backgroundTransparency = backgroundTransparency`, so constructing with no argument writes `undefined` over the prototype's `backgroundTransparency: 1` just as surely as an explicit `= undefined` default would; no later "only when passed" guard can undo a field that has already been written. ⚠ Deleting a `= nil`/`= undefined` default therefore does NOT disarm this — the `@param` is the hazard. When a parameter's *absence* must mean "keep the class default", take it as a **plain** parameter and assign it guarded — the pattern `StringWdgt`'s constructor already documents: `@backgroundColor = backgroundColor if backgroundColor?`. This has now bitten twice: the layout-spec follow-ups (absence sentinels swallowed by CS defaults) and the **dropped-background-fill** arc, where the resulting `undefined` reached `ctx.globalAlpha` and a specified `backgroundColor` silently painted NOTHING with no error anywhere ([`docs/archive/dropped-background-fill-investigation.md`](docs/archive/dropped-background-fill-investigation.md)). ⚠ Note the second half of that failure is general: **an invalid value handed to a canvas property is not necessarily loud** — HTML5 says to ignore it, SWCanvas stores it raw, and a fill can then composite at NaN coverage.
- **How a constructor takes its parameters is a stated convention: a positional head for IDENTITY (cap 4), one trailing `opts = {}` object for CONFIGURATION, read `opts.key ? default`.** The decisive rule is the **hole test** — *if any call site must pass `undefined` to reach a later argument, the parameter list is wrong* — because a hole proves the skipped parameter is configuration, not identity. Law, exemptions and the decision procedure: [`docs/architecture/constructor-and-parameter-conventions.md`](docs/architecture/constructor-and-parameter-conventions.md); the sweep that brought the tree onto it (P0–P9, CLOSED): [`docs/archive/constructor-parameter-conformance-plan.md`](docs/archive/constructor-parameter-conformance-plan.md); the gate that holds BOTH repos to it — `buildSystem/check-call-arguments.js`, real parsers over every call site (src, harness, macros, rigs) at an exact zero: `HOLE` (the doc's callers test, each hole printed with its witness), `EXTRA_ARGUMENT` (an argument no parameter receives — judged only where its target is certainly among the definitions it reaches) and `POSITIONAL_INTO_OPTIONS` (`@`, a literal, a `new`… landing in an `opts = {}` slot) — and the button family's move to one options object: [`docs/archive/argument-holes-both-repos-plan.md`](docs/archive/argument-holes-both-repos-plan.md); the two arity rules: [`docs/archive/call-arguments-gate-plan.md`](docs/archive/call-arguments-gate-plan.md). ⚠ A paren-less call swallows a sibling written on the next line (`[ f "a",⏎ f "b" ]` is ONE element, `f("a", f("b"))`) — the conventions doc §5 lists the spellings that compile to something else. ⛔ Converting a base class's signature ripples through every subclass `super` — do a family in ONE commit. - **Every widget is PLACED and SIZED in integer pixels — enforced.** Bounds round at the *desired* funnel (`Widget._moveToNoSettle`/`__commitExtent`) AND at every layout *producer* that computes a fractional target (axis ticks, horizontal-stack distribution, `center()`-based centring, corner-internal sizing, …); the always-on guard `Widget._assertBoundsWellFormed` (called from each bounds-commit leaf) `console.error`s `NON_INTEGER_GEOMETRY` (fractional applied `@bounds`) and `NON_FINITE_GEOMETRY` (NaN/Infinity), **both wired into the headless runners' fail-gate** — a fractional placement fails the suite even when the pixels match. - **How a build flavour excludes code — NAMED PARTS and existence guards.** The partition lives in **[`buildSystem/parts.json`](buildSystem/parts.json)**: named **parts**, each owning directories, optionally declaring `requires` / `eager` / `vendor` / `assets`. ⛔ The `inHomepage` boolean that used to sit on each part is DELETED (arc 5): **inclusion is the profile's business now**, listed explicitly in `buildSystem/profiles/<name>.json`, so a part added tomorrow does not silently join production. ⭐ One of them, `app-kit`, is not an app slice but the **shared BASE LAYER** the others derive from (`WindowedApp`, the toolbar, and the creator-button family with its base `CreatorWdgt`): when several parts derive from a group of classes, no existing part is the right home — invent the part and have every consumer `requires` it. ⛔ A base class can cross a part boundary ONLY under `requires` (a `class X extends Y` line has no seam to await in), which is also why an EAGER part can never derive from a lazy one. `if Automator?` / `if DemoMenus?` / `if PinoutsOverlay?` / `world.pinouts?.…` / `return unless LayoutElementAdderOrDropletWdgt?` guards make a part's absence a no-op at every call site, and **`buildSystem/check-part-edges.js` fails the build on an unguarded core reference into a part** — or into a MEMBER a part installs onto a core class (`*TestSupport.installOnto`), where an existence test on the member itself (`@m?()`) is a guard too — the one structural defence for a failure mode nothing else catches (the suite runs the harness page, which carries every part;
