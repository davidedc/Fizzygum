# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Fizzygum is

A CoffeeScript GUI framework — a "web operating system" (windows, desktop, drag-and-drop, live in-system editing tools) rendered on a single HTML5 `<canvas>`. It descends from Morphic.js. ~510 `.coffee` files live in `src/`.

## Build, run, watch

Prerequisites are installed **globally, not via `npm`**: `coffee` (`npm i -g coffeescript`), `terser`, `python3`, and `fswatch` (watch script only). `npm test` is a do-nothing stub — see Testing.

- **Build:** `./build_it_please.sh` → output goes to `../Fizzygum-builds/latest`.
  - **A build FLAVOUR is a PROFILE, not a flag:** `--profile <name>` selects `buildSystem/profiles/<name>.json`, and a plain invocation builds `dev`. A profile declares three facts — `parts` (which slices of the partition ship), `form` (`compile-at-boot` | `precompiled`), `entries` (which entry pages ship) — plus `sources` (`background` | `lazy` | `none`: WHEN the class source text and its meta-system arrive), which is required iff `form` is `precompiled` and forbidden otherwise, because a compile-at-boot build's sources ARE its world — and `buildSystem/buildProfile.py` DERIVES everything else from them: the `js/tests` symlink and `BUILDFLAG_LOAD_TESTS` (does the `harness` part ship?), which build gates run, the boot-bundle prelude, whether the SWCanvas bundle and its ~90 MB of `font-assets/` are built (does any shipped entry render through SWCanvas?), and whether the pre-compile driver runs (`form`). Adding a flavour is adding a file. ⛔ `--homepage` and `--notests` are DELETED (arc 5) and now fail loudly; the shipped profiles are:
    - `dev` (default) — every part, compiled in the browser, all three entry pages.
    - `dev-precompiled` — `dev`, but booting from a PRE-COMPILED image instead of compiling in the browser: same parts, `sources: "lazy"`, and `index.html` ONLY. Measured 3219 ms → 59 ms to world-ready ([`docs/measurements/boot-timing-2026-07-31.md`](docs/measurements/boot-timing-2026-07-31.md)), against +5.3 s of build. ⚠ The single entry page is FORCED, not a simplification — an image is harvested by booting ONE page, and `index-sw.html`/`worldWithSystemTestHarness.html` preset `FIZZYGUM_EAGER_ALL_PARTS`, so they would ingest sources for classes that image never defined (`Cannot set properties of undefined (setting class)`, measured twice). ⇒ the suite does NOT run on this tree, and does not need to: `dev` stays the default. This is for the human who opens `index.html` and drives the world by hand.
    - `homepage` — the production artifact: pre-compiled, `sources: "lazy"`, `index.html` only, and thirteen parts — `core` plus TWELVE that are all **LAZY**: `app-kit` (the shared base layer the app parts derive from) / `meta-tools` / `maps` / `plots` / `spreadsheet` / `authoring` / `examples-icons` and the five one-class `example-*` doors of the Examples folder. A lazy part is absent from `js/pre-compiled.js`, so naming one keeps the feature and still leaves it off the first load. ⭐ Since every non-core part is lazy, production's eager image IS the core image — `homepage` and `lean` emit a byte-identical `js/pre-compiled.js`.
    - `dev-notests` — `dev` minus the `harness` part.
    - `lean` — the appliance artifact: `core` only, pre-compiled, and `sources: "none"` — no `js/coffeescript-sources/` at all. ⚠ Because `sources: "none"` **forbids shipping a lazy part at all** (a lazy part's source *is* its code — the image is harvested by booting `index.html`, where lazy parts do not load), the appliance necessarily has neither the spreadsheet nor the **Makers** — no Docs, Slides, Dashboards, Draw, Patch programming, Generic panel or Super Toolbar — and correctly no desktop icons for them: `createDesktop` asks `world.parts.canEverProvideClass` before drawing each icon, so a profile that cannot produce an app simply draws none — an icon whose click could only reject is worse than no icon. An appliance that wants those back wants `sources: "lazy"`, which is a different artifact. ⚠ It also cannot inspect or rewrite itself, and a loaded snapshot's class-level source edits are refused with one clear `inform` (per-widget `{"$src"}` edits still work — those need only the compiler, which every profile ships).
  - `--includeVideoPlayer --includeVideos` — bundle the video player + assets. (Still flags: they are per-invocation opt-ins, not properties of an artifact. `video-player` is the one part left carrying `requiresFlag`.)
  - `--noSyntaxCheck` — skip the build-time CoffeeScript syntax gate (see Testing). Deliberately NOT a profile field: a profile describes an artifact, not how carefully you checked it.
- **✅ Test a change — PREFERRED / DEFAULT:** `./build_and_test.sh` — full build **+** the whole SystemTest suite run **headless, in parallel shards, at `speed=fastest`, dpr 1** (~1 min on a many-core box). This is the standard way to verify a behaviour change; don't watch the suite in a browser (~15 min) or run tests one-by-one unless debugging a single test. One-time setup: `cd ../Fizzygum-tests && npm i` (Puppeteer).
- **Build + boot-smoke gate:** `./build_and_smoke.sh` builds (incl. the syntax gate) then headless-boots BOTH interactive entry pages (`index.html` native, `index-sw.html` SWCanvas), failing on any console error — a lighter boot-only check (use when a full suite run is overkill).
- **Watch + rebuild on save:** `./build_as_soon_as_anything_changes.sh` (`fswatch` over `src/`; the syntax gate runs on every save).
- **Run:** open `../Fizzygum-builds/latest/index.html` in a browser. It loads over `file://`; no dev server needed. (`index-sw.html` is the same world rendered by the SWCanvas software backend; `worldWithSystemTestHarness.html` is that plus the test harness.)
- **Find duplicated code:** `./find_duplicated_code.sh` — jscpd (devDependency) over `src/**/*.coffee`, no compile step (CoffeeScript is tokenized natively); console/JSON/markdown/HTML reports plus an LLM-handoff clone-pair list land in `duplication-report/` (gitignored). Tuning + gotchas (jscpd silently skips >1000-line files at its defaults — config raises the caps): `docs/tooling/duplicated-code-detection.md`.
- **Find SIMILAR (renamed/structural) code:** `./find_similar_code.sh` — jsinspect AST matching over a CoffeeScript-1-compiled ES5 mirror (`buildSystem/coffee-to-js-mirror.js`); catches the renamed/near-miss clones jscpd's exact-token scan can't. ⚠ its reports carry compiled-JS line numbers — navigate by file + `@method` name. Both scanners take `--tests` to scan the sibling `Fizzygum-tests` repo (harness + node scripts) instead. The recurring **re-audit → triage-ledger → LLM-session cycle** (incl. the `duplication-report/triage-report.md` ledger convention and its end-of-arc snapshot into `docs/done/`) is documented in the same docs file: `docs/tooling/duplicated-code-detection.md`.

The build must run from a repo whose parent directory is named `Fizzygum-all`, and aborts otherwise. The layout it hard-codes `../` paths into:
```
Fizzygum-all/
  Fizzygum/          ← this repo (source only)
  Fizzygum-builds/   ← build output (generated; never hand-edit — created for you if absent)
  Fizzygum-tests/    ← SystemTests + Automator source (separate repo; absent ⇒ no js/tests link
                       and the two tests-repo gates self-skip)
```
(`Fizzygum-website/` appears in the build's own abort message and in older docs, but nothing reads it — it is not checked out here and is not needed to build or test.)

## Architecture (the non-obvious parts)

- **How a build is assembled and selected — the partition, the profiles, and what each profile DERIVES rather than declares — is in [`docs/architecture/build-and-packaging.md`](docs/architecture/build-and-packaging.md).** Read it before touching `parts.json`, `buildSystem/profiles/*.json`, `buildProfile.py`, `build.py` or `build_it_please.sh`. Its RUNTIME half — how a page boots (the two paths: compile-at-boot vs the pre-compiled image), when the reflective layer arrives, and how `world.parts` (`PartsRegistry`) brings a LAZY part in behind an already-running world — is §2/§5 of that same doc, illustrated by [`docs/explainers/boot-and-lazy-parts.html`](docs/explainers/boot-and-lazy-parts.html). Read that before touching `src/boot/*`, `PartsRegistry`, or any door that awaits a part.
- **Subsystem references live in `docs/architecture/`** — present-tense, verified-against-src: the layout/settle engine ([`docs/architecture/layout.md`](docs/architecture/layout.md): the world cycle, settle tiers, ordered down-walk, constraint-box sizing, the layout-spec FAMILY (§4.2 — one spec object per attachment, knob-vs-record lifecycle), claimsSpace, the standing zero-invariants, the new-layout rulebook), the affine transform islands ([`docs/architecture/transforms.md`](docs/architecture/transforms.md): TransformFrameWdgt islands, TransformSpec, the two-vocabulary law, the lens declarations, pinned anchors, plane-mapped input, the island buffer cache), and the scrolling-container family ([`docs/architecture/viewports-and-planes.md`](docs/architecture/viewports-and-planes.md): `ViewportWdgt` the chrome composite, the plane ROLE + `ScrolledPaneWdgt`, the runtime `scrollPolicy 'auto'|'never'` crop⇄scroll flip, the scrolled-content contract, and why `PanelWdgt` is purely the SURFACE class). Read those before touching any of the three subsystems.
- **The rendering backend is a BUILD-TIME property of the entry page.** `buildSystem/build.py` writes every entry page from the single source `src/index.html`, substituting a `window.FIZZYGUM_USE_SWCANVAS` preset plus the matching boot-bundle tag for the `<!--FIZZYGUM_BOOT_SCRIPTS-->` placeholder (its `ENTRY_PAGES` table): `index.html` → native + `js/fizzygum-boot-native-min.js`; `worldWithSystemTestHarness.html` and `index-sw.html` → SWCanvas + `js/fizzygum-boot-sw-min.js`. Both bundles come out of ONE terser pass — `build_it_please.sh` fronts the same minified boot JS with two different engine preludes — so the second flavour costs a concatenation, not a build. There is **no runtime `?sw=` switch**: a page missing the preset `console.error`s at boot. To add an entry page, add a row to `ENTRY_PAGES`.
- **Source-as-text + in-browser compilation.** `buildSystem/build.py` does *not* compile `src/` classes. It wraps each class's CoffeeScript source into an escaped JS string and hands it to the **`SourceVault`** — `SourceVault.store("<Name>", "<escaped>", "<part>")`, grouped into ~15 `sources_batch_*.js` files; the browser compiles them at boot with the bundled CoffeeScript compiler. The vault (`src/boot/source-vault.coffee`, **first** in the boot bundle so it exists before any batch runs) is the ONE registry of source text: `SourceVault.names()` enumerates, `SourceVault.get name` reads, and each entry carries the **part** it belongs to — which is what lets a slice of the system be loaded on demand rather than all-at-boot. The escaping (`"`→`＂`, `\`→`⧹`, `\n`→`⤶`) is encoded by build.py's `STRING_BLOCK` and decoded in exactly one place, `SourceVault.store`. ⛔ The predecessor — one `window.<Name>_coffeSource` global per class, discovered by suffix-scanning `Object.keys(window)` — is **RETIRED (arc 4)** and gated (`buildSystem/check-source-vault.js`): do not reintroduce either the naming convention or a window scan. A profile with `form: "precompiled"` instead ships a `pre-compiled.js` image for instant startup. That image is GENERATED at packaging time by `../Fizzygum-tests/scripts/generate-pre-compiled-headless.js`, which such a build invokes: it boots the freshly-built page at `?generatePreCompiled` — the one mode in which `Class`/`Mixin` accumulate the JS they compile into `window.JSSourcesContainer.content` — then reads that string out and writes the file from Node. (An ordinary boot does NOT accumulate it: that would be ~2.4 MB of string nothing reads.) The production boot check asserts `window.preCompiled === true`, so a tree that silently shipped the stub fails. Only `src/boot/*` is compiled to JS at build time. ⚠ **That source text is a build INPUT to any precompiled artifact**, even one whose profile says `sources: "none"` — the driver harvests the image by booting the tree in compile-at-boot mode, so the text (and `js/src/dependencies-finding-min.js`) must exist during the build and is dropped after the driver runs, never skipped earlier.
- **No imports / no module system.** Zero `require`/`import`; every class is a global. Load order is auto-discovered by `src/boot/dependencies-finding.coffee`, which *regex-scans source text* for `extends X`, `@augmentWith X`, and `new X`. To reference another class just name it — but use those literal forms so the dependency finder sees the edge.
- **Class hierarchy:** `TreeNode` → `Widget` → `PanelWdgt` → … → `WorldWdgt`, the global singleton `window.world`. Widgets form a tree, painted recursively; a Widget with no owner is never drawn.
- **Writing a widget class — the house rules are in [`docs/architecture/widget-authoring-guidelines.md`](docs/architecture/widget-authoring-guidelines.md)**: one section per decision a widget author faces (constructor shape and the `@param` trap, the `_buildAndConnectChildren` pair, class-level field declaration, the `createAppearance` factory, when `_reLayoutChildren` is yours to define, settle tiers, self-invalidation, input, menus, pin setters, stepping, teardown, type tests vs capability queries), each with the gate that enforces it, plus a checklist and a skeleton. Read it before adding a `*Wdgt`. Its companion [`docs/measurements/widget-practices-survey-2026-08-14.md`](docs/measurements/widget-practices-survey-2026-08-14.md) is the dated audit of how the 270 existing widgets score on 28 facets — every CONVERGED facet has a gate/census/architecture doc behind it, every PATCHWORK one has none.
- **Meta classes.** `src/meta/Class.coffee` and `Mixin.coffee` parse each source at runtime, which is what enables live inspection/editing of any class from inside the running world.
- **Rendering** is a *damage-rectangles* repaint loop on the canvas. A widget invalidates only ITSELF — `@_changed()` (just this widget) / `@_fullChanged()` (it + its subtree), both PRIVATE: never call them on another widget (widget-citizenship point 2, gated by `check-invalidation-receivers.js`); cross-object repaint goes through intent-named public methods on the receiver (e.g. `world.noteWallpaperChanged()`, `world.caret.noteTextChanged()`) — there is no general-purpose public repaint verb. Pluggable `*Appearance` objects do the drawing — every paint body draws widget-local LOGICAL coordinates through the ctx matrix inside the ONE preamble `Appearance._paintInLocalScope` (the appearance paint convention, law + declared device-space exceptions: [`docs/architecture/appearance-paint-convention.md`](docs/architecture/appearance-paint-convention.md)); widgets opting into `BackBufferMixin` cache themselves to an offscreen canvas.
- **Software 3D (SW3D) for Fizzytiles.** The `src/fizzytiles/` app ("fridge magnets" / Fizzytiles) runs the LiveCodeLang program its tiles compile to and **software-renders** it — no WebGL, no twgl (deleted). It uses **SW3D**, the userland software-3D engine (`examples/sw3d.js`) vendored from the SWCanvas repo (see `scripts/vendor-swcanvas.sh` + the boot-bundle assembly in `build_it_please.sh`, gated by the `vendor/swcanvas.pin` SHA). SW3D ships in *every* bundle, but the SWCanvas it sits on does not: the SW bundle carries the full engine, while the native bundle carries only SWCanvas's subtractive **3D-core** dist target (Surface + DepthBuffer + Texture3D + Triangle3DOps, ~14 KB minified vs ~263 KB) — pixel-identical on the 3D path, proven by SWCanvas's own `examples/3d-core-node.js` witness. `FridgeMagnets3DCanvasWdgt` rasterizes each frame into an `SWCanvas.Core.Surface` (+ `DepthBuffer`/`Triangle3DOps`) and blits it; its matrix stack is `LCLTransforms`. Determinism: the animation clock is event time under the Automator (`docs/archive/fizzytiles-sw3d-port-plan.md`).
- **Dataflow / spreadsheet engine — the SECOND drain station.** `WorldWdgt.doOneCycle` runs **two parallel drain stations**: `recalculateDataflow` (settles VALUES) runs BETWEEN `runChildrensStepFunction` and `recalculateLayouts` (settles GEOMETRY), and the coupling is one-way — dataflow may dirty layout, never the reverse. ONE engine (`world.dataflow`, `src/dataflow/`) serves two clients: **spreadsheet** cells wired by formula references and **patch-programming** widgets wired by connections (`@wires`, a list of `WireSpec` records, mirrored into edges by `world.dataflow.ensureWireEdges`). A change marks nodes **stale**; values are **pulled** at recompute time (notifications carry no values); the forward/reverse edge index is derived and never serialized. Design: [`docs/specs/dataflow-engine-spec.md`](docs/specs/dataflow-engine-spec.md); depth: [`src/dataflow/CLAUDE.md`](src/dataflow/CLAUDE.md) + [`src/spreadsheet/CLAUDE.md`](src/spreadsheet/CLAUDE.md); measured convergence (typical 1 pass): [`docs/measurements/dataflow-measurements.md`](docs/measurements/dataflow-measurements.md).
- **Window drag-embed (dwell-to-arm).** Float-dragging a *window* over a receptive container embeds it only after a ~450ms **dwell** (held still within 7px; `ActivePointerWdgt` state machine — `dwellToArmMs`), so a window never nests by accident; an unarmed release lands it on the desktop, and dragging a nested window out ejects it. Plain (non-window) payloads still embed instantly (the payload-class rule, `requiresDeliberateEmbedding`). A window's internal-vs-external skin is **DERIVED from its parentage** (`FrameWdgt.isInternal` = nested in a real container), re-derived on every re-parenting — there is no stored flag and no manual switch button. All drag feedback is ephemeral overlays. Design + as-built deviations: [`docs/specs/drag-embed-interaction-spec.md`](docs/specs/drag-embed-interaction-spec.md); arc history: [`docs/archive/drag-embed-implementation-plan.md`](docs/archive/drag-embed-implementation-plan.md).
- **Mixins** are applied with `@augmentWith SomeMixin` (eight of them: six in `src/mixins/`, plus `ParentStainerMixin` and `WidgetCreatorAndSmartPlacerOnClickMixin` in `src/app-kit/`, beside their creator-button consumers). The whole widget tree can be duplicated through the `Duplicator` engine (`src/duplication/`) and, via the `src/serialization/` `Serializer`/`Deserializer` pair, serialized to a versioned JSON file — duplication is also how SystemTests snapshot state. **All serialization / deserialization / duplication internals — format, traversal contract, per-class protocol, `file://` I/O — are documented in one place: [`docs/architecture/serialization-duplication-reference.md`](docs/architecture/serialization-duplication-reference.md).** Mixins are a **permanent mechanism with a narrow remit** (standing policy + inventory: [`docs/architecture/mixins.md`](docs/architecture/mixins.md)): a behaviour that must be *injected into* classes on unrelated branches (overriding framework hooks) stays a mixin; a responsibility that can be *delegated out* becomes a plain collaborator class instead (the `MacroToolkit` pattern — `world.macroToolkit`, in `src/macros/`); a mixin with a single consumer or a single subtree is misfiled and gets folded into the consumer or a shared base.

## Testing

**The build runs 26 project-specific STATIC GATES, and their complete index — what each one checks, what it provably CANNOT see, and how to sanction an exception — is [`docs/architecture/lint-and-static-checks.md`](docs/architecture/lint-and-static-checks.md).** Read it before concluding a class of bug is uncaught, and before writing a new gate. ⚠ Every gate has a stated blind spot, and a RUNTIME twin exists beside a static gate whenever that blind spot is "the name resolves but the thing behind it is wrong": `check-menu-actions.js` catches a menu-dispatched parameter that is UNREAD and structurally cannot catch one read as the wrong THING or one MISSING altogether, so `fg menusweep` clicks every menu item; and no text scan can decide whether an advertised pin is serviceable — a `PinSpec` names its setter by STRING and `pins()` is COMPOSED, so a subclass can NARROW it — so `fg pinsweep` resolves every advertised pin and drives every `announces` fixture. Both are `fg gauntlet` wave-A legs.

Two fast automated checks complement the (manual/browser) SystemTests:
- **Build-time syntax gate** (`buildSystem/check-coffee-syntax.js`, run automatically by `build_it_please.sh`): since the ~510 class/mixin sources ship as text and compile in-browser, this is what catches CoffeeScript *parse* errors at build time. It LOADS the real `src/meta/Class.coffee`/`Mixin.coffee` and compiles each source the same *fragmented* way the browser does — a whole-file `CoffeeScript.compile(src,{bare:true})` is NOT faithful (it false-fails on most files). Skip with `--noSyntaxCheck`.
- **Headless boot smoke** (`../Fizzygum-tests/scripts/smoke-boot-headless.js`, via `./build_and_smoke.sh` or `cd ../Fizzygum-tests && npm run smoke`): headless-boots both shipped interactive entry pages (`index.html` native, `index-sw.html` SWCanvas) and fails on any console/page error — catching the load-order/runtime faults the syntax gate cannot. Its **`--production` mode** (what `fg homepage` runs, on a `--profile homepage` tree) additionally asserts the production tree booted from the pre-compiled image, ships no SWCanvas payload, and survives a whole-world **snapshot round-trip** — the only gate anywhere that loads a snapshot on a production tree, and therefore the only one that can catch shipping code referencing a field a production build does not have.

- **ONE world teardown, two callers.** `WorldWdgt._teardownWorldStructureNoSettle` is a **shipping** core with a single contract: *after `fullDestroyChildren()`, the world holds no reference to anything just destroyed, and no bookkeeping that assumed it still exists* — the off-tree containers, the app slots, `errorConsole`/`lastEditedText`, the tooltip/pop-up/handle/momentum/highlight collections, the damage-suppression depth, the one-shot `infoDoc*` flags. Restoring what the world should LOOK like afterwards is the **caller's** job: pristine grey + the harness resolution for the test teardown (`_resetWorldNoSettle`, which arc 3 moved OUT of core into `../Fizzygum-tests/Automator-and-test-harness-src/WorldTestSupport.coffee`), the file's contents for `loadWorldSnapshot`. That split is a real seam (only the test teardown wants a pristine LOOK) — and it is why the two used to look unrelated: only the *look* half is product-vs-test. They were hand-synchronised twins until 2026-07-29 and had drifted twice in two days in opposite directions, leaking real product bugs (a DESTROYED `errorConsole` swallows every later paint error in the session; the additive-only `infoDocFlags` restore can never clear a flag the file lacks). ⚠ Anything you add to a teardown belongs in the core unless it restores appearance. (Until arc 3 the PINOUT sets were the exception — their declarations were region-stripped, so a product build had no such fields and the core could not touch them. They now live on the optional `world.pinouts` collaborator, so `@pinouts?.reset()` sits in the core like everything else and that seam is gone.) Gates: the suite's `RESETWORLD_INCOMPLETE` ratchet (below) covers the core through `resetWorld`; `world.teardownHygiene.*` in `../Fizzygum-tests/scripts/serialization-roundtrip-headless.js` covers it through `loadWorldSnapshot`. Arc: [`docs/archive/teardown-shared-core-plan.md`](docs/archive/teardown-shared-core-plan.md).
- **World-teardown completeness ratchet** (`WorldWdgt._auditWorldResetCompletenessNoSettle` — like `_resetWorldNoSettle` above it lives in `../Fizzygum-tests/Automator-and-test-harness-src/WorldTestSupport.coffee`, not here, and is installed onto the world at boot, so it is behind no flag on any build shipping the `harness` part — called at the end of `resetWorld`): all SystemTests share ONE page per shard, so any world-level state `_resetWorldNoSettle` forgets leaks into the next test in that page — a bug class that stayed invisible to every gate for years, because it only bites when the consuming predecessor happens to share a page with the victim. The guard fingerprints the world's own mutable state at the first teardown and re-checks it at every later one, `console.error`ing `RESETWORLD_INCOMPLETE` — **wired into the headless runners' fail-gate** like `NON_INTEGER_GEOMETRY`. If it fires: reset the field in `_resetWorldNoSettle`, or name it in `WorldWdgt._worldStateAuditExemptions` **with its reason** (monotonic counters and deliberate measurement switches are legitimate exceptions; anything that can reach a render is not). Audit + full inventory: [`docs/archive/resetworld-teardown-completeness-audit-plan.md`](docs/archive/resetworld-teardown-completeness-audit-plan.md); bug class: `../Fizzygum-tests/DETERMINISM.md` §2d. Beside it at the same seam runs the **object-lifetime audit** (`WORLD_INVENTORY_*` tokens, `src/dev-tools/WorldInventory.coffee`), covering the ratchet's blind spots — class statics, collaborator/module state, the DOM, and widget IDENTITY (it names an escaped or zombie widget) — doctrine + failure-reading guide: [`docs/architecture/world-lifetime-and-inventory.md`](docs/architecture/world-lifetime-and-inventory.md).

Behavioural tests are **SystemTests**: each one drives the running world from a high-level **macro** (a generator that asks the live world where things are and synthesises real input events), then compares canvas screenshots pixel-by-pixel against reference images. The Automator source and the tests themselves (300+ today — `fg status` prints the live count) live in the sibling `Fizzygum-tests` repo (not here); every build whose profile ships the `harness` part SERVES them from there through the `js/tests` symlink — nothing is copied, so a test change needs no rebuild. (Macros are the only authoring path — the old input *recorder* has been removed.)
- **Author:** write the test directly as a macro — the framework-side helper toolkit lives in **`src/macros/`** (engine `Macro.coffee` + `MacroToolkit.coffee`, reached as `world.macroToolkit`) and is documented in **`src/macros/CLAUDE.md`**; see also the `/author-macro-test` skill in `Fizzygum-tests`.
- **✅ Run the whole suite — PREFERRED / DEFAULT:** `./build_and_test.sh` (build + suite), or against an existing build `cd ../Fizzygum-tests && npm test` (= `scripts/run-all-headless.js`). Runs the whole suite **headless, in parallel shards, at `speed=fastest`, dpr 1** — ~1 min on a many-core box (vs ~15 min watching a browser). `npm run test:all` is the single-process variant. This is the default way to verify a change. The suite can also run **headless under Safari/WebKit** (Chrome stays default) as a cross-engine determinism check — `--browser=webkit` / `npm run test:webkit`, reusing the same references; see `../Fizzygum-tests/CLAUDE.md`.
- **Run one (debugging a single test):** open the built `worldWithSystemTestHarness.html`, then `world.automator.loader.loadAndRunSingleTestFromName('SystemTest_name')`; or headless `node scripts/run-macro-test-headless.js SystemTest_<name>`.
- **Determinism (the suite asserts byte-exact pixels — keep it deterministic):** render/layout/input code must be a pure function of the **event stream** and **final geometry**, never of wall-clock timers (`setTimeout`/`Date.now`), frame/cycle counts, or intermediate layout passes — those diverge at **dpr 2 under parallel load** (heavy cycles starve timers and drain multiple events per frame). The contract, the recurring bug-class with worked case law, and the diagnosis playbook (deterministic heavy-cycle reproduction, pixel-delta forensics, disable-the-mechanism proof) are in **`../Fizzygum-tests/DETERMINISM.md`** — read it before touching the rendering loop, `_reLayout`, or `ActivePointerWdgt` input recognition.

## Conventions & gotchas

- **`docs/` is bucketed by what a file IS — keep the split honest** (map + full filing rules: `docs/README.md`): `architecture/` how it works NOW · `specs/` behaviour contracts · `plans/` ACTIVE arcs only · `archive/` closed/falsified/parked plans, verbatim + status-stamped, indexed in `archive/INDEX.md` · `measurements/` dated snapshots · `tooling/` dev-tool how-tos. The standing loop: new arc → `plans/`; arc closes → `git mv` to `archive/` + stamp + INDEX line; durable residue → the subsystem's `architecture/` doc **in the same arc**; every open/deferred item gets a `docs/BACKLOG.md` line pointing at its owning plan section.
- **One class per file; filename must equal the class name** (`Widget.coffee` ↔ `class Widget`). `build.py` keys off this.
- **`Wdgt` is the widget suffix, and it is now universal** — the `*Morph` legacy inherited from Morphic.js is fully migrated: zero `*Morph` classes remain, and the handful of surviving mentions are provenance comments plus `Widget`'s defensive `/(Wdgt|Morph)$/` strip. New widgets are `*Wdgt` from the start. ⚠ The lesson of that migration outlives it and applies to ANY class rename: a rename here is *not* always pixel-free — menu/hierarchy labels strip `Wdgt`, so renaming a class whose colloquial name is DRAWN (menu items, for instance) shifts that label and forces SystemTest screenshot recapture; verify per class, and do a family in ONE verifiable batch, since each rename is a whole-tree identifier+file+serialization sweep.
- **`undefined` is the codebase's ONE absence value** — spelled the way the language spells it. `null` appears only where a foreign API demands it (`JSON.stringify`'s replacer arg, DOM `onload = null`); the `null-literal` stink holds that tail at 8. ⛔ The `nil = undefined` global is **RETIRED** and gated at zero by the `nil-literal` stink — do not reintroduce it or any other alias for a language primitive. (It was a 2017 workaround for CoffeeScript 1→2 changing default parameters from `if (a == null)` to ES2015 semantics, which fire on `undefined` only; by the end it was load-bearing at about a dozen call sites, cost a writable global plus a boot-order dependency, and had leaked into the reflective layer as *emitted source*. History: `docs/archive/nil-global-retirement.md`.)
- **⚠ A CoffeeScript `@param` in a constructor signature ASSIGNS THE FIELD UNCONDITIONALLY — so it SHADOWS the class-level default. This is true WITH OR WITHOUT a default on the parameter.** `constructor: (@backgroundTransparency) ->` compiles to a plain `this.backgroundTransparency = backgroundTransparency`, so constructing with no argument writes `undefined` over the prototype's `backgroundTransparency: 1` just as surely as an explicit `= undefined` default would; no later "only when passed" guard can undo a field that has already been written. ⚠ Deleting a `= nil`/`= undefined` default therefore does NOT disarm this — the `@param` is the hazard. When a parameter's *absence* must mean "keep the class default", take it as a **plain** parameter and assign it guarded — the pattern `StringWdgt`'s constructor already documents: `@backgroundColor = backgroundColor if backgroundColor?`. This has now bitten twice: the layout-spec follow-ups (absence sentinels swallowed by CS defaults) and the **dropped-background-fill** arc, where the resulting `undefined` reached `ctx.globalAlpha` and a specified `backgroundColor` silently painted NOTHING with no error anywhere ([`docs/archive/dropped-background-fill-investigation.md`](docs/archive/dropped-background-fill-investigation.md)). ⚠ Note the second half of that failure is general: **an invalid value handed to a canvas property is not necessarily loud** — HTML5 says to ignore it, SWCanvas stores it raw, and a fill can then composite at NaN coverage.
- **How a constructor takes its parameters is a stated convention: a positional head for IDENTITY (cap 4), one trailing `opts = {}` object for CONFIGURATION, read `opts.key ? default`.** The decisive rule is the **hole test** — *if any call site must pass `undefined` to reach a later argument, the parameter list is wrong* — because a hole proves the skipped parameter is configuration, not identity. Value/geometry tuples (`Point`, `Rectangle`, `Color` — ~950 `new Point` sites), foreign-API records (the `events-input/` family, reached through `fromBrowserEvent`), and published user-facing spellings (`new SliderWdgt 0, 100, 30, 10`, typed into spreadsheet formulas) stay positional however long they are; there a hole means *reorder*, not an options bag. Law, exemptions and the decision procedure: [`docs/architecture/constructor-and-parameter-conventions.md`](docs/architecture/constructor-and-parameter-conventions.md); the sweep that brought the tree onto it (`positional-hole` 51 → 0 hard, and the honest counter `check-argument-holes.js` at its floor of 2 — P0–P9, CLOSED): [`docs/archive/constructor-parameter-conformance-plan.md`](docs/archive/constructor-parameter-conformance-plan.md). ⛔ Converting a base class's signature ripples through every subclass `super` — do a family in ONE commit. Constructor changes are serialization/duplication-SAFE (both instantiate via `Object.create`; the ctor is never run), so only explicit `new X(...)` / `super` sites matter — in BOTH repos.
- **Value classes are IMMUTABLE — never write a field of a `Point`/`Rectangle`/`Color`/`ShadowInfo`/`TransformSpec` after construction; there is deliberately NO `copy()` on Point/Rectangle.** Operations return new instances, `this`, or a canonical constant (`Point.ZERO`, `Rectangle.EMPTY`, `ShadowInfo.noShadow()`, the interned `Color.*`) under an exact-`===` bar; immutables are shared, not cloned, on deepCopy (`keptByReferenceOnDeepCopy`). Policy, inventory, shortcut rules, and the serializer/duplicator traps: [`docs/architecture/immutable-value-classes.md`](docs/architecture/immutable-value-classes.md). ⚠ A class-level constant may reference its OWN class (deferred-static mechanism) but never another class — the boot dependency scanner only sees declaration-level `new X` edges (details in that doc §3).
- **Every widget is PLACED and SIZED in integer pixels — enforced.** Bounds round at the *desired* funnel (`Widget._moveToNoSettle`/`__commitExtent`) AND at every layout *producer* that computes a fractional target (axis ticks, horizontal-stack distribution, `center()`-based centring, corner-internal sizing, …); the always-on guard `Widget._assertBoundsWellFormed` (called from each bounds-commit leaf) `console.error`s `NON_INTEGER_GEOMETRY` (fractional applied `@bounds`) and `NON_FINITE_GEOMETRY` (NaN/Infinity), **both wired into the headless runners' fail-gate** — a fractional placement fails the suite even when the pixels match. Fractional *desired* geometry is kept on the side (e.g. the `StretchLayoutSpec` edge fractions for stretchable-panel/desktop children); internal *content* rendering (vector icons, charts, rotated strokes) is legitimately fractional. Integer placement is **necessary but not sufficient** for a back buffer to be byte-identical to a direct draw. Policy + rationale + the back-buffer FP caveat: [`docs/architecture/integer-pixel-placement-and-sizing.md`](docs/architecture/integer-pixel-placement-and-sizing.md); the enforcement arc + the divider-drag reproportion sub-pixel-sensitivity case-law: [`docs/archive/fractional-widget-bounds-investigation-plan.md`](docs/archive/fractional-widget-bounds-investigation-plan.md). Widgets are placed and sized in integer pixels **in their own plane**; under an affine `TransformFrameWdgt` island the *screen-family* queries (`screenBounds()`/`localPointToScreen()`/…, every name contains `screen`) are DERIVED, post-transform, and possibly fractional, while the layout-box family (`width`/`height`/`bounds`/`center`/…) stays plane-local and integer — the two-vocabulary law, see [`docs/archive/affine-geometry-api-plan.md`](docs/archive/affine-geometry-api-plan.md).
- **Tests are SERVED through a symlink, never copied.** The build points `../Fizzygum-builds/latest/js/tests` at the sibling `Fizzygum-tests/tests` directory (`ln -sfn`), so a test edit, a freshly captured reference, or a brand-new test directory is live **with no rebuild** — only framework/harness `.coffee` changes need one. A build whose profile omits the `harness` part carries no `js/tests` entry at all. ⚠⚠ Never aim a recursive delete at that path: `rm -rf <link>/` (trailing slash) deletes the REAL suite, and `find -L` descends into it; the build owns it via one `ln -sfn` and one guarded `[ -L p ] && rm -f p`.
- **The two test manifests are DERIVED, and gitignored.** `Fizzygum-tests/tests/testsManifest.js` + `testsAssetsManifest.js` are written by `Fizzygum-tests/scripts/generate-tests-manifests.js` — once by the build, and again at the startup of every headless runner / capture script, so a stale manifest is impossible. (`build.py` no longer generates them.)
- Edit only `src/**/*.coffee`. Never edit `../Fizzygum-builds/**` — it is regenerated every build.
- **Never `git stash` in this repo.** On 2026-07-05 a `stash pop` silently emptied both the working tree AND the stash list (a `.gitattributes` warning is implicated); recovery required digging git dangling blobs out by hand. Use a WIP commit or a `git worktree` for clean-tree A/B comparisons.
- **How a build flavour excludes code — NAMED PARTS and existence guards.** The partition lives in **[`buildSystem/parts.json`](buildSystem/parts.json)**: named **parts** (21 today), each owning directories, optionally declaring `requires` / `requiresFlag` / `eager` / `vendor` / `assets`. ⛔ The `inHomepage` boolean that used to sit on each part is DELETED (arc 5): **inclusion is the profile's business now**, listed explicitly in `buildSystem/profiles/<name>.json`, so a part added tomorrow does not silently join production. Every shipping directory belongs to exactly one part; a `src/` directory no part claims FAILS the build (`check-shippable-coverage.js`). Core = the product, and is 58.8% of shippable source bytes. A part also OWNS its non-source files: `assets` (copied) and `vendor` (assembled from vendored pieces) are written by `build.py` only for parts that ship, which is how a flavour stops shipping a file without anyone maintaining a prune list. Production ships twelve parts besides core and **every one of them is lazy**, so its eager image IS the core image. ⭐ One of them, `app-kit`, is not an app slice but the **shared BASE LAYER** the others derive from (`WindowedApp`, the toolbar/creator-button family and their mixins): when several parts derive from a group of classes, no existing part is the right home — invent the part and have every consumer `requires` it. ⛔ A base class can cross a part boundary ONLY under `requires` (a `class X extends Y` line has no seam to await in), which is also why an EAGER part can never derive from a lazy one. `if Automator?` / `if DemoMenus?` / `if PinoutsOverlay?` / `world.pinouts?.…` / `return unless LayoutElementAdderOrDropletWdgt?` guards make a part's absence a no-op at every call site, and **`buildSystem/check-part-edges.js` fails the build on an unguarded core reference into a part** — the one structural defence for a failure mode nothing else catches (the suite runs the harness page, which carries every part; the smoke boots and rotates a widget; neither clicks the menu item that would throw). ⚠ A guard is right for INCLUSION and wrong for LAZINESS: a lazy part's entry point must await `world.parts.ensureLoaded`, because `if X?` would silently swallow the user's click. ⛔ TWO exclusion mechanisms were retired and are gated at zero — do not resurrect either, and **do not invent a replacement marker syntax**: the lesson is that invisible, text-level exclusion is the wrong tool, not that its spelling was wrong.
  - per-REGION `# »>>` comment spans cut out of the source TEXT (**arc 3**, `check-region-markers.js`): accreted for eight+ years unaudited, and was stripping PRODUCT code out of production — core sizing and `_reLayout` machinery, class constants that silently became `undefined`, public API, and `_deferredSettleDeclare` while six shipping call sites still called it.
  - per-FILE markers `# this file is excluded from the fizzygum homepage build` (43 files) / `# this file is only needed for Macros` (2) / `# this file is only needed for VideoPlayer` (**0 carriers — a live exclusion rule matching nothing, for years**) (**arc 4**, `check-whole-file-markers.js`). A marker states a file's fate invisibly, one file at a time, so the shape of a production build could only be learned by opening 499 files — and it cannot say which files belong TOGETHER, so it cannot express a part, so it cannot support loading a slice on demand.
  If code is dev/test-only, RE-HOME it: promote it (it is product), move it to `../Fizzygum-tests/Automator-and-test-harness-src/` as a `*TestSupport` class installed onto the core prototype at boot (it is test machinery), extract it into its own guarded collaborator (`PinoutsOverlay`, `DemoMenus`), or put it in a part.
