2. The plan: four stages

1 · Today  →  2 · The four stages  →  3 · Worked examples

The whole program is one idea applied four times: things that are properties of an artifact stop being runtime switches and scattered markers, and become explicit build-time or load-time decisions. Each stage also permanently deletes the old mechanism it replaces — that's a rule, not a hope (see the doctrine below). Each stage has a full, self-contained plan in docs/plans/; this page is the guided tour.

Status (2026-07-30): stages 1 and 2 have LANDED IN FULL. The renderer is a build-time property of the page, and the »>> region mechanism is gone — all 63 sites re-homed, all three build regexes deleted, a build gate holding every kind at zero, and the one menu topology unified (owner-designed, one recapture wave). Stages 3 and 4 are still ahead.
The completion doctrine. Progressive migrations tend to leave the old mechanism alive “until the last site moves” — and then it never dies. Here the rule is: once a stage starts retiring a mechanism, it finishes inside that stage. A build gate forbids new uses of the old pattern from day one; the stage cannot close until the count of old sites is zero and the machinery itself (regexes, scanners, scripts) is deleted. Mixed old/new states are legal only inside an open stage, never between stages.

Stage 1 · Backend split — the renderer becomes a property of the page — LANDED

One ~18 s build pass now produces one shared tree with two boot bundles, and each entry page bakes in its renderer — the ?sw=1 parameter is deleted:

The native bundle can be small because SWCanvas's 3D primitives — all that Fizzytiles needs — are architecturally separable: a new ~18 KB swcanvas-3d-core build target of the SWCanvas library (plus SW3D at ~5 KB, minified).

Stage 1 also externalizes the pre-compiled-image generator: the in-page zip-and-download machinery is deleted; a small cross-platform Node driver boots the built page headless, reads the accumulated compiled JS out of it, and writes pre-compiled.js directly. (This also un-breaks precompiled builds on macOS — the old driver only ever ran under WSL.) The 90 MB font copy stops shipping in homepage trees.

Newly possible: a product page whose boot payload is ~40 KB instead of 314 KB; a homepage deploy 90 MB lighter; precompiled builds that actually generate on this machine; the single-file-save arc gets its “SWCanvas-free bundle” for free.

Stage 2 · One world — the homepage stops being a fork — LANDED (menu unification closing)

Two world designs used to exist: the dev/test world (menus grown by accretion) and the homepage world (a marker-stripped, reorganised fork). Stage 2 converged them into one design, re-homing the in-file region markers rather than replacing them with a nicer marker syntax:

A 2026-07-28 census classified all 58 homepage regions, and execution largely confirmed it: ~17 were mis-marked product code (including chunks of the layout engine — promoting them fixed the homepage), ~28 were test/demo machinery to relocate or extract, ~11 dead accretion to delete. A mechanical audit of what the homepage referenced but did not ship found the truncation was worse than the census recorded: _deferredSettleDeclare was stripped while six shipping call sites called it. Two of the three build-script regexes are now deleted and a gate keeps the count from rising. Menu unification (owner-designed, one recapture wave) closes the stage.

Newly possible: the homepage runs the same layout engine and the same menus as the world you develop in; “is this dev-only?” has one answer (where the code lives), not a per-line marker; the latent homepage crashes (excluded classes used by shipping widgets) are gone.

Stage 3 · Dynamic parts — code loads when it's needed

The 470 classes get partitioned into a core plus named parts (pilot: fizzytiles). A part is: its classes' sources, any vendor payload (for Fizzytiles, the 23 KB of 3D engine), and a manifest entry. Two supporting pieces:

  • SourceVault — one registry object replaces the ~470 window.<Name>_coffeSource globals. Every source is stored with its part name; enumeration stops being a scan of window.
  • Derived dependencies — the same scanner that orders classes at boot is aggregated per part at build time, so part→part requires are computed, never hand-written; a cycle (or a hard reference from core into a part) fails the build.

Two rules keep this safe. Tests never lazy-load: the harness page eagerly loads every part at boot, so the suite's timing and pixels are exactly today's (mid-test loading would break determinism; the lazy path gets its own dedicated test). And saved worlds stay self-sufficient: loading a snapshot that contains part widgets first loads those parts, automatically.

Newly possible: a product page that boots only the core and grows on demand; “experimental” is a part you don't ship rather than a marker; the whole-file exclusion mechanism is replaced by the partition (and deleted); inspectors-as-a-part becomes an option.

Stage 4 · Profiles — “a build flavour” becomes data

After stage 3, any shipping flavour is fully describable by four choices. Stage 4 makes that literal — a profile manifest:

{ "name":    "homepage",
  "parts":   ["core"],           // which parts ship
  "form":    "precompiled",      // instant boot vs compile-at-boot
  "sources": "background",       // eager | background | lazy | none
  "entries": ["index.html"] }

The --homepage conditionals in the build script are deleted; “homepage” is just the first manifest. One thing ships in every interactive profile: the CoffeeScript compiler (208 KB). That's not nostalgia — FizzyPaint's brushes are CoffeeScript source injected at click-time, spreadsheet formulas are CoffeeScript (loading a saved sheet recompiles its cells), and saved worlds can carry user-injected methods. A compiler-less Fizzygum would be a look-but-don't-touch kiosk.

Newly possible: “package a build with exactly what I want in it” is a one-manifest job; the lean profile drops the 2.5 MB of sources and the inspectors for appliance-style artifacts; the future single-file precompiled page reuses the same machinery.

What never changes

  • Everything still runs by double-clicking a file — every mechanism above is file://-safe by construction (script injection, no fetch).
  • The dev build stays compile-at-boot and live-editable — sources in the page, inspectors on everything.
  • The test suite keeps byte-exact determinism — every stage's gate includes “zero unexplained pixel churn”.
