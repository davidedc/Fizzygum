Mouse, touch, and the one pointer pipeline

Companion to docs/architecture/input-and-gestures.md (authoritative). Covers how mouse and touch input are modelled, how W3C Pointer Events are used, what typical interactions do on each kind of pointer, and how the test system covers both.

Two facts shape everything below. First, there is no separate mouse pipeline and touch pipeline: the browser boundary is W3C Pointer Events, so a mouse, a finger and a pen all arrive as the same four event types, distinguished only by a per-event pointerType string. Second, widgets never see pointer kinds — they see two TIERS of verb, and the tier is legible in the name's shape. The fact tier narrates the phases of a stroke and interprets nothing: pressBegan, pressMoved, pressEnded, hoverEntered, hoverExited, hoverMoved. The gesture tier states a meaning the hand has already certified: activated (this stroke, examined, meant an activation), contextMenuRequested, scrolledBy. A widget author choosing between pressBegan and activated is choosing between a raw phase and a guarantee — and every decision about what a gesture means for a given kind of pointer lives in exactly one class, the hand (ActivePointerWdgt). A finger opening a context menu and a right-click opening it reach the very same widget method, contextMenuRequested, by two different triggers.

1 · The browser boundary: Pointer Events, one listener family

Yes, Pointer Events are used — they are the only input listeners. The world attaches pointerdown / pointermove / pointerup / pointercancel to the canvas (plus wheel, contextmenu with preventDefault, and keyboard listeners). A finger is not emulated — it is a first-class pointer kind.

  • touch-action: none on the canvas is what stops the browser from panning/zooming instead of delivering events — with pointer events, preventDefault() does not stop browser panning; the CSS property does.
  • setPointerCapture at the down keeps a stroke's moves and its up arriving even when the pointer leaves the canvas mid-drag.
  • Safari's proprietary gesturestart/gesturechange listeners are kept as no-ops beside the pointer listeners until pinch is derived from two pointerIds (a BACKLOG item — today the system is single-pointer).

2 · The event family, and the two doors into the one queue

Every input — mouse, touch, pen, real or synthesized — becomes a value of the same PointerInputEvent family (src/events-input/: one base + the four down/move/up/cancel subclasses), carrying pointerType, pointerId, isPrimary, pressure, buttons/modifiers and a world-coordinate position. There are exactly two ways such a value is born — and they are only two doors into the same room: a browser listener calls @fromBrowserEvent, a test macro calls @synthetic or @syntheticTouch, and what comes out of either is the identical value shape. Everything downstream — the queue, the hand, the widgets — consumes these values and only these values, with no memory of which door they came through:

The queue is the determinism backbone: events drain once per world cycle, ordered by their own event time, and every timing decision downstream (multi-click recognition, the drag-embed dwell, the press-and-hold below) is a function of event time — never Date.now() or setTimeout — so a replayed stream produces byte-identical pixels regardless of machine load.

A touch down states its own position. A mouse has hover, so by the time it presses, the hand already knows where it is. A finger's first event is the press — so a position-carrying down runs the move pipeline first, then the press. Between touch strokes there is no pointer position at all (see the pointer-absence state below).

3 · The grammar: one geometry, one grammar per pointer kind

There is no "touch mode". Every decision keys on the stroke's pointerType (recorded at each down), so a hybrid laptop gets every stroke right: mouse strokes take the classic paths byte-identically, and 'pen' takes the mouse grammar (it hovers and has a barrel button). For a 'touch' stroke the hand runs a press-and-hold recognizer, built on the same event-time template as the drag-embed dwell. The whole question the recognizer answers is: do this stroke's drags mean what a mouse's would?

The recognizer in detail:

  • A stroke is armed for mouse semantics at the down when nothing competes for a plain drag: chrome surfaces answer ownsDragsStartingOnMe() (window title strips, handles, sliders, dividers, palettes), and where no ancestor viewport claimsPlainDragsForScrolling() (the open desktop), a drag needs no hold either.
  • Over scrollable content, a touch stroke arms only by holding still (pressAndHoldMs, 500 ms of event time within the 7 px grabDragThreshold). The hold fires the context gesture's own verb — contextMenuRequested, the pressed widget's titled context menu at the press point — and from then on the stroke's drags mean what a mouse's would (hold-then-move lifts; hold-then-release keeps the menu and dispatches no click, exactly as a secondary press never fires activated).
  • A pre-hold move past the threshold commits the stroke as a plain drag — a scroll — for its whole life, and a scroll owes nothing at its end: the release dispatches no click (_strokeOwesNoClick). This matters because a drag-scroll carries the pressed row along with the finger, so press-widget equals release-widget by construction — without the rule, every scroll would click what it pressed.
  • At a touch stroke's end the hover world dissolves: every widget under the stroke is told the pointer left, the over-list empties, and a pointer-absence flag starves the per-cycle hover re-sync — nothing is "under" a pointer that is not there. Mouse strokes keep today's persistent pointer-under state.
  • pointercancel (the browser confiscating a stroke) aborts cleanly: pressed state and the recognizer are cleared, no click fires, an already-open hold menu stays.
  • The virtual keyboard is summoned per edit, keyed on the starting tap: a touch tap into a text field brings up the hidden DOM input (the on-screen keyboard's anchor); a mouse or pen click does not. There is no per-device setting.
Where the branch lives. Three consumers read the stroke's arming (strokeMeansMouseDrag()): the hand's float-drag arms (lift only when the stroke means a mouse drag), the viewport's drag-to-scroll step (an un-armed touch stroke scrolls even over draggable content — and inherits the wheel's at-edge escalation to an enclosing pane), and the pressMoved channel (an un-armed touch drag neither extends a text selection nor paints — it scrolls, and nothing else). Mouse strokes answer "armed" without reading any state, which is what makes the whole grammar provably inert for the mouse.

4 · Typical interactions, side by side

The four finger gestures, as timelines (time flows left to right; every threshold is event time):

You want to…Mouse / penFinger
press a button click tap — a tap is a click, same dispatch
open a widget's context menu right-click (or ctrl-click) press and hold ~½ s — the same titled menu at the press point; it stays after the release, an outside tap dismisses it
scroll a list of draggable cards wheel (or the scrollbar); a drag on a card lifts it plain drag scrolls — the cards stay parented; at the pane's edge the leftover escalates to an enclosing pane
pick a card OUT of that list drag it hold until the menu blinks up, then drag — the hold armed the lift (the menu goes away, the card rides the finger, drop embeds per the usual dwell rules)
move a window drag its title strip the same, immediately — chrome never demands a hold
drag a slider / resize by a handle drag it the same, immediately (chrome again)
select text in a scrolling document drag over it (selects; the pane may also scroll — the classic mouse behaviour) plain drag scrolls only; hold, then drag selects
drag anything on the bare desktop drag it the same, immediately — nothing competes for the drag, so no hold is demanded
edit a text field click into it — your hardware keyboard types tap into it — the on-screen keyboard's input is summoned for that edit

5 · How the test system covers both kinds

Behavioural coverage is the SystemTest suite: each test drives the live world from a macro that synthesizes real input events through the same queue the browser feeds, then compares screenshots byte-exactly against committed references. Pointer-kind coverage comes in three layers:

5a · The mouse suite is the default

All 330 tests run as mouse strokes (the macro verbs are mouse-intent: click, right-click, wheel, press-drag-release), matched against the mouse reference baseline. This is the inner loop (fg presuite, ~1 min at dpr 1) and three gauntlet legs (dpr 1, dpr 2, WebKit).

5b · Dedicated touch tests — ordinary suite members

Eight tests synthesize touch strokes directly, through four L1 verbs (syntheticEventsTouchTap/TouchHold/TouchDrag/TouchDragFromHeldPress) — the same event classes, the same queue, no special mode. They witness the grammar itself: the hold opens the titled menu (and the world menu on bare desktop); the one-frame contrast where the same drag scrolls for a finger and lifts for a mouse; hold-then-drag lifts; chrome drags need no hold; the keyboard summon (assertion-only, no pixels); and three tablet-extent tests that declare testScreenExtent: [1024, 768] — a small-screen world where the world menu, a window drag and the docked toolbar's overflow chevron all work under a finger. They run in every suite run, mouse or finger, because their event streams are touch either way.

5c · The whole corpus replays as a finger

The suite is not naively run twice. Under --pointer=finger (?pointer=finger on the harness page) the macro toolkit translates every mouse-intent verb into the touch gesture carrying the same intent, in the verb bodies — the 300+ committed macro sources are untouched:

the macro saysa finger run performs
clicka tap
right-click / open the menu of…a press-and-hold (its real ~½ s, never speed-compressed — a recognition window is not playback)
press, drag, releasehold-then-drag (the intent is MOVE)
wheel on a panedrag-swipes on that pane — successive, clamped to the pane's span (a notch has unlimited reach, a finger has an arm's)
hover movesnothing — a finger has no hover (unless the hand carries a payload, which still travels)
drag a handle / slider / resizera plain drag — chrome needs no hold

319 of the 330 tests replay this way. The other 11 are declared mouse-only by meaning in their metadata (pointerKinds: ["mouse"] plus a mandatory mouseOnlyReason) — tests whose subject is hover pixels, a mouse-vs-finger contrast, or wheel-notch mechanics (exact clamp landings and round-trips are properties a finger's swipes do not have; the spreadsheet takes no drag-scroll at all). An undeclared test that cannot replay under finger is treated as a finding, never silently skipped.

5d · Two reference baselines, one directory axis apart

Finger pixels legitimately differ from mouse pixels (no hover highlights, hold menus where right-click menus were), so finger runs match their own references, on a directory axis below the density segment — absence means mouse:

tests/<Test>/automation-assets/<OS>/…/SWCanvas/ceilPixRatio_<N>/           ← mouse references
tests/<Test>/automation-assets/<OS>/…/SWCanvas/ceilPixRatio_<N>/finger/    ← finger references

The loader requires the segment in finger runs and excludes it in mouse runs — both ways, so a wrong-kind reference can never satisfy a run. The Automator version in the filename never changed for any of this: the mouse capture path is byte-identical with the finger machinery in place (gated at every commit, not asserted), so no re-baseline was ever owed.

The one thing the suite structurally cannot see is the browser listener layer itself: the harness detaches the world's listeners and drives the queue directly, so the suite proves the event classes and the grammar, not the DOM wiring. That gap is covered separately — headless probes dispatch real PointerEvent {pointerType:'touch'} at the canvas of the built pages (both engines) and assert the hand received the stroke, and the boot smoke keeps the listener block alive. Capture is Chrome-only; WebKit runs reuse the same SWCanvas references, as they do for the mouse.
