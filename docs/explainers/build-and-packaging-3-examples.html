Example A · Double-clicking index.html

Today — one maximal artifact:
boot bundle 314 KB (85% renderer)
compiler 208 KB
sources 2.5 MB — every class
compile all ~470 classes (~seconds)
world (everything resident)
After stage 1 — same flow, right-sized bundle:
native bundle ~40 KB
compiler 208 KB
sources 2.5 MB
compile ~470 classes
world
After stage 3 — core only; parts wait until used:
native bundle ~40 KB
compiler 208 KB
core sources only
compile core classes
world (parts load on demand)
Stage 4, a precompiled profile — instant boot:
native bundle ~40 KB
pre-compiled.js
world — immediately
sources arrive in the background (or lazily, or never — the profile decides)

Example B · Launching Fizzytiles (the 3D fridge-magnets toy)

Before
Its 10 classes compiled at boot like everything else; the 3D engine rode in the 314 KB bundle whether or not you ever open a fridge. Clicking the launcher just instantiates the app.
Stage 1
The native page carries only the ~23 KB 3D sliver (3D core + SW3D) instead of the whole 263 KB renderer. Behaviour identical.
Stage 3
Fizzytiles is a part. The boot payload contains none of it. Clicking the launcher runs: ensure part → inject 23 KB vendor + its sources → frame-paced compile → open — sub-second, once per session. A saved world containing a fridge loads the part automatically before deserializing. The suite is unaffected: the harness page eager-loads all parts, so the Fizzytiles SystemTests see exactly today's world.

Example C · Running the test suite

Before
The headless runners open the harness page with ?sw=1 (a runtime switch since deleted): every pixel is computed in software, so screenshots hash identically on every machine and browser.
Stage 1
The harness page bakes the SW renderer in; the parameter is deleted. Same engine, same flags, same pixels — the stage's acceptance gate is literally “zero reference-image churn”.
Stage 2
Test menus and machinery arrive as additive registrations from the harness instead of living inside product classes — the world under test is the product world plus contributions. One menu-unification recapture wave, then stable.
Stage 3
Nothing changes, by rule: parts are code, and code already persists across a whole test run today. The harness eager-loads all parts at boot; resetWorld() between tests resets state (widgets, world collections) and never unloads code — so there is no reload cost, and no new nondeterminism, in a 268-test sequence.

Example D · Shipping the homepage

Before
Build with --homepage: markers strip 53 files and 58 regions (including, it turns out, parts of the layout engine); the precompiled image is generated by a WSL-only script — on macOS the step silently no-ops and the homepage boots the slow way; 90 MB of fonts are copied in for a renderer the page can't use.
Stage 1
Homepage tree = native bundle only, no fonts (−90 MB), and the precompiled image is generated by the cross-platform driver — working, and verified by a gate that asserts the page really boots precompiled.
Stage 2
The homepage is no longer a fork: same world design, same (full!) layout engine, same menus — minus the test/demo contributions it simply doesn't load. The marker mechanism is gone.
Stage 4
“Homepage” is a 6-line manifest (parts: core · form: precompiled · sources: background). The build script has no homepage-specific code left.

Example E · Packaging a custom artifact (“just the spreadsheet, instant boot”)

Before
Not possible. There is exactly one shipping flavour (homepage), its content chosen by markers scattered through the source.
Stage 4
Write a manifest:
{ "name": "sheet-appliance",
  "parts": ["core", "spreadsheet"],
  "form": "precompiled",
  "sources": "none",
  "entries": ["index.html"] }

The build emits a tree with only those parts, pre-compiled, no source strings, no inspectors. What still ships: the CoffeeScript compiler — spreadsheet formulas are CoffeeScript, and a saved sheet recompiles its cells on load. (This is why “eject the compiler” is not a profile option: paint brushes, formulas, scripts, and saved-world $src records all compile at runtime. The profile machinery knows this and refuses a contradiction rather than shipping a broken artifact.)

Example F · Saving the world as a single file (the TiddlyWiki move)

A separate, already-locked plan gives Fizzygum a “save this whole world as one .html” feature — code and world state in a single self-contained file that re-opens into that world. The stages here make that artifact better without changing its plan:

Stage 1
The saved page embeds the ~40 KB native bundle instead of carrying a hard-disabled 285 KB renderer (the option the single-file plan had banked as “later” arrives for free).
Stage 3
The saved file embeds core plus exactly the parts the world had loaded — the assembler enumerates the SourceVault, and a snapshot can only reference classes whose part is loaded, so the file is self-consistent by construction. A world that never opened Fizzytiles saves smaller.
Stage 4
A precompiled single-file page (instant-boot appliance in one file) becomes the profile machinery applied to the single-file assembler.
