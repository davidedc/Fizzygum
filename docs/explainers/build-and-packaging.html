How build & packaging works

The visual companion to the authoritative reference, docs/architecture/build-and-packaging.md. The history of how the system got this shape lives in docs/archive/build-arc-1…5-*.md.

Two facts make Fizzygum's packaging unusual. First, there is no module system: every class is a global, shipped as escaped source text and compiled in the browser — so "what an artifact contains" means which named slices of source text it carries, which pages it has, and whether classes arrive as text-to-compile or as a pre-compiled image. Second, everything runs by double-clicking a file (over file://, no server), so all loading is script injection. A CoffeeScript compiler ships in every artifact — not as a dev tool, but because paint brushes, spreadsheet formulas, saved-world records, and Fizzytiles programs are all compiled from source at runtime.

Two files decide everything

A part — a named slice that comes and goes as a unit

Every shipping directory belongs to exactly one of the 20 parts; a source file no part claims is a build failure. A part owns up to four kinds of thing — sources (dirs), copied files (assets), assembled vendor payloads (vendor), and boot-bundle pieces (bootPrelude) — and all four appear or vanish together with it.

Two properties are deliberately separate questions:

  • Inclusion — is the part in this artifact at all? Decided by the profile. An absent part must be a no-op at every call site, via the class-existence guard idiom (if DemoMenus?); a build gate fails on any unguarded core reference to a part-owned class.
  • Eagerness — at boot, or on demand? A lazy part (today 13 of the 19 non-core parts, and every single one production ships) is fetched by world.parts when something launches it — and since classes are source text, its source arrives with it. A lazy part's entry point awaits world.parts.ensureLoaded(…) instead of using a guard: a guard answers "is it here?", a lazy part needs "get it here".

Laziness pays because a lazy part's classes are absent from the pre-compiled image — the image is harvested by booting index.html, where lazy parts by definition do not load. That is what let production keep the desktop's Examples documents (which build maps, so the part cannot simply be dropped) while still taking the map artwork off the first load: −55.8 KB, −5.1% of the image, nothing visibly changed.

Two traps that only bite lazy parts.

1 · An awaiting entry point must keep its already-loaded path synchronous. On every build the test suite runs, parts are eager and long since present — so going through .then anyway defers by a microtask, which moves the effect a whole world cycle later, and the suite measures cycles. Hence world.parts.whenAllLoaded ["maps"], -> …, which runs its callback inline when the parts are already in and only falls back to a promise otherwise — one method rather than a conditional copied into every door, and the same shape the reflective layer uses.

2 · Not every call site can await. An app is easy — its launch is fire-and-forget. A creator button is not: both the click and the drag path consume its createWidgetToBeHandled() return value synchronously, so there is no seam to defer through. The fix is partition, not cleverness — put the button in the part it creates from, and its very existence proves the part is loaded.

3 · On a precompiled tree the part needs the META-SYSTEM first. Ingesting a part's sources means new Class / new Mixin, and ordering them means findLoadOrder — and none of the three is in the image (Class and Mixin are the only two classes it lacks). So a part load awaits ensureMetaSystemLoaded(), ~39 KB — and pointedly not the whole reflective layer, which would fetch every eager batch and hand back the entire saving that made the part lazy in the first place.

There are no flavour flags. ./build_it_please.sh builds the dev profile; --profile homepage builds production; an unknown argument is a hard error that lists the available profiles. (--noSyntaxCheck and the video-copy switches remain invocation knobs by design: a profile describes an artifact, not how carefully you checked it or where its gigabytes get copied from.)

Entry pages, bundles, and what boot looks like

Each entry page bakes in its renderer and its part-loading policy. index.html loads the native bundle (~32 KB: boot + the 3D core Fizzytiles needs); index-sw.html and the test-harness page load the full software-renderer bundle (byte-exact pixels for the suite). The harness page loads every part at boot, so the 269 tests always see the whole world — laziness is a product-page behaviour only.

The reflective layer

"The reflective layer" is the class source text plus the meta-system that parses it — what lets Fizzygum show and rewrite its own code. On a precompiled tree it is not needed to run the world, so it becomes a policy (sources): background — fetch it once the world is up; lazy — fetch it on first demand (opening an inspector, or loading a snapshot that carries class-level source edits); none — ship none of it (no inspectors; snapshots with class-level source edits are refused with a clear error). What never varies: the runtime compiler and compileFGCode ship in every profile — runtime compilation is product behaviour, not a dev affordance.

The safety net

GateFails the build / check when…
check-shippable-coveragea source file exists that no part claims
check-part-edgescore references a part-owned class without a guard
check-source-vault · check-whole-file-markers · check-region-markersa retired mechanism (source-string globals; either marker kind) reappears — tombstones held at zero
profile validationan unknown key, a nonexistent part/page (a rename fails the build instead of silently shipping less), a profile without core, sources: none with meta-tools or a lazy part
fg homepagethe production tree misbehaves — it boots it, asserts it really is precompiled, carries no SWCanvas payload, survives a whole-world snapshot round-trip, fetches nothing at boot under sources: lazy, and opens an inspector successfully
build-tree-fingerprint comparea packaging change produces an UNPREDICTED tree delta (baseline before → predict in words → compare)
One habit matters more than any single gate: the behavioural suite never builds a production tree. fg gauntlet proves behaviour; fg homepage (and the lean smoke) prove packaging. A packaging change verified only by the gauntlet is unverified.
