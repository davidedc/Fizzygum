1. How Fizzygum is built, loaded, and shipped today

1 · Today  →  2 · The four stages  →  3 · Worked examples

Fizzygum is a whole desktop-like environment drawn on a single HTML5 <canvas>. Everything you see — windows, menus, text, apps — is one program painting one canvas. Two constraints shape everything on this page: it must run by double-clicking a file (over file://, no server), and it must stay live-editable from inside itself (you can open any class in an in-world inspector and change its source while it runs).

Three repos, one build

The source lives in Fizzygum/, the test suite in Fizzygum-tests/, and the build output in Fizzygum-builds/latest/ — which is generated wholesale, never edited. A full build takes about 18 seconds.

The unusual part: classes ship as text

There are no imports and no module system — every class is a global. The build does not compile the 470 classes. It wraps each class's CoffeeScript source code into an escaped JavaScript string, and the browser compiles everything at boot using a bundled CoffeeScript compiler. Load order isn't declared anywhere; a boot script discovers it by scanning the source text for extends, @augmentWith, and new X.

Why this odd design? Because the source being present in the page is what powers the in-world class inspectors and live editing — and because over file:// a page cannot fetch() its own files, so everything loads by <script> injection, which strings survive happily.

What is inside the boot bundle?

Here's the surprise: the boot bundle is 314 KB, and Fizzygum's own boot code is only ~15 KB of it. The rest is SWCanvas — a complete software renderer — plus helpers:

Why is a whole software renderer in there?

Fizzygum can paint through two renderers:

  • Native canvas — the browser's own 2D engine. Fast, what humans use.
  • SWCanvas — a software renderer that computes every pixel itself, so output is byte-identical on every machine and browser. That determinism is the foundation of the test suite: all 268 SystemTests compare screenshots down to the exact pixel hash. SWCanvas draws text with BitmapText, which needs 90 MB of font atlas data.

Which renderer runs is decided at build time, by the page. Each entry page presets window.FIZZYGUM_USE_SWCANVAS and loads the boot bundle carrying exactly that engine: index.html is native (plus the ~14 KB SWCanvas 3D core that SW3D needs), index-sw.html and worldWithSystemTestHarness.html are full SWCanvas. A page missing the preset console.errors at boot rather than guessing. To pick a backend you pick a page.

This replaced a runtime ?sw=1 URL switch on a single dual-engine artifact — the native bundle went 314 KB → 32 KB, and --homepage ships no SWCanvas payload and no font-assets/ at all. Landed by arc 2 (archive/build-arc-2-backend-split-precompile-plan.md).

There is one twist that matters later: the Fizzytiles app (the fridge-magnets live-coding toy) renders 3D in software through SW3D — which sits on a tiny slice of SWCanvas (~18 KB of its 263 KB). So even the pure-native experience needs that sliver. Today the sliver is inseparable from the whole.

The second flavour: --homepage

Besides the dev build there is one shipping flavour, born years ago for the public homepage. It differs in three ways:

  1. It drops whole FILES using an in-file marker. A file carrying a “# this file is excluded from the fizzygum homepage build” comment is simply never emitted for this flavour.
    There used to be a second, per-REGION mechanism as well — a »>> comment opened a span, cut out of the source text by regex. Arc 3 retired it: all 63 sites were re-homed (promoted where they were product, moved to the tests repo where they were test machinery, or extracted into their own collaborator class), and a build gate now keeps the count at zero. See the creaks table below for why.
  2. It boots instantly from a pre-compiled image. A special page mode compiles everything, accumulates the compiled JS, and packages it as pre-compiled.js — Fizzygum generating its own fast-boot image (a quine-like trick). Sources still load afterwards, in the background, so inspectors keep working.
  3. Test machinery is dead-code-eliminated via if Automator? guards.

Why does this fork exist at all? The old test system recognised widgets by strings and IDs, which froze the UI: menus could only ever grow, and they grew byzantine. At launch time the pragmatic fix was a separately-designed homepage with the accretion stripped out. The modern macro test system asks the live world where things are, so that constraint is gone. The markers are now gone with it (arc 3); what remains of the fork is the menu topology itself, which the owner is converging in that arc's last phase.

Where this creaked (audited 2026-07-28) — and what has since been fixed

FindingConsequence
The 314 KB bundle was ~85% renderer, shipped to every page — plus 90 MB of fonts in every build — for an engine only tests use. FIXED (arc 2). The backend is baked into the page, so the native bundle is 32 KB and --homepage carries neither the SWCanvas payload nor the fonts.
The region markers were never audited. ~14 of the 58 homepage regions turned out to be product code: core layout machinery, layout constants, public API. FIXED (arc 3). It was worse than the census recorded: a mechanical audit of what the homepage referenced but did not ship found _deferredSettleDeclare stripped while six shipping call sites called it, plus password-field obfuscation, the addAsSibling* pair and the halo's stack adjusters. The homepage really was running a truncated layout engine. All promoted; the mechanism is retired and gated at zero.
The pre-compiled-image generator script only ran under WSL (it fished a zip out of the Windows Downloads folder), so on macOS it silently did nothing — homepage instant-boot was inoperative, masked by the compile-at-boot fallback. FIXED (arc 2). The homepage build now invokes a headless Node generator and the boot check asserts window.preCompiled === true — the stub boots perfectly well, so only the assertion can tell a real image from a generator that produced nothing.
Everything loads at boot: every app, every inspector, all sources — whether or not this session will ever use them. Boot does maximal work; there is no way to ship “just what this artifact needs”.
