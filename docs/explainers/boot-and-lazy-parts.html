Fizzygum · explainer

How the boot happens, and how parts arrive later

Companion to docs/architecture/build-and-packaging.md (authoritative) and to the build & packaging explainer, which covers how an artifact is assembled. This one covers what happens when you open it.

Two facts shape everything below. First, there is no module system: every class is a global, and classes are shipped as escaped source text that the browser compiles at boot — or, for a precompiled artifact, as one already-compiled image. Second, Fizzygum runs by double-clicking a file, over file:// with no server — so there is no fetch and no XHR, and every load in this document is a <script> tag injected into the head, wrapped in a promise (loadJSFilePromise, which tries three times before rejecting).

1 · The entry page: two presets and one bundle tag

All three entry pages are generated from the single source src/index.html. The build substitutes two window.* presets plus the matching boot-bundle <script> for a placeholder comment; everything else on the page — the splash image, the canvas, the onload hook — is shared verbatim.

<script>window.FIZZYGUM_USE_SWCANVAS = false; window.FIZZYGUM_EAGER_ALL_PARTS = false;</script>
<script src="js/fizzygum-boot-native-min.js"></script>
Entry pageRendererAll parts eager?What it is
index.htmlnative 2Dno the only page where laziness is real — production ships just this one
index-sw.htmlSWCanvasyesthe same world, software-rendered
worldWithSystemTestHarness.htmlSWCanvasyesthat plus the test harness — what the suite drives

Why the two test-side pages force every part eager. A part arriving during a test would be frame-paced, therefore cycle-count-dependent, therefore exactly the nondeterminism class the suite is built to exclude. So they preset FIZZYGUM_EAGER_ALL_PARTS and the suite's world is shaped as it always was. The consequence worth remembering: a SystemTest can never observe laziness — it would pass while proving nothing. That gap is filled by separate Node rigs (§7), and it is structural, not a shortcut.

2 · The boot bundle, and why its order is load-bearing

The bundle is the page's first script. It is assembled by concatenating CoffeeScript in a fixed order, compiling it once and minifying it. The order is not cosmetic:

#PieceWhy here
1source-vault.coffee First, always. Every generated sources_batch_*.js is a list of SourceVault.store(…) calls, so the vault must exist before any batch can run.
2partsManifest (generated) window.FIZZYGUM_PARTS — each part's batch files, eagerness and vendor payloads. It is in the bundle rather than fetched because the batch loader needs it immediately.
3globalFunctions.coffee the boot sequence itself, plus loadJSFilePromise and the reflective-layer machinery
4extensions/* prototype extensions (Array, Object, Math, String, canvas…) that must exist before any class runs
5each shipping part's bootPrelude the same, but contributed BY a part — today only numbertimes.coffee, which Fizzytiles' LiveCodeLang needs. A part owning its own boot piece is why the build script no longer holds a fact about a part.
6the build stamp buildVersion, from the source COMMIT and never the wall clock — so two builds of a clean tree at the same commit are byte-identical

3 · Two boot paths

Which one runs is decided by the profile's form, and the difference is fundamental: on a compile-at-boot tree the sources ARE the world, so they must be compiled before there is anything to start. On a precompiled tree the world is already running before any source text is considered.

form: compile-at-boot  — the dev builds

boot bundle
pre-compiled.js (a stub) + CoffeeScript compiler
Class + Mixin sources → compile by hand
dependencies-finding
every eager part's batches
compile + EXECUTE all ~500 classes
world exists → doOneCycle

form: precompiled  — production and the appliance

boot bundle
pre-compiled.js (the real image) + compiler
world exists → doOneCycle
…later, and only if asked: the reflective layer

The stub is not a placeholder you can ignore. A compile-at-boot tree still ships a js/pre-compiled.js — one that sets preCompiled = false. The production boot check therefore asserts window.preCompiled === true: the stub boots perfectly well, so only that assertion distinguishes a real image from a generator that produced nothing.

And the image is harvested by booting the tree itself. The packaging driver opens the freshly-built page at ?generatePreCompiled — the one mode in which Class/Mixin accumulate the JS they compile — then reads that string back out and writes the file from Node. Which is why the source text is a build INPUT to every precompiled artifact, even one whose profile says sources: "none": the text must exist during the build and is dropped after the driver runs.

4 · The reflective layer, and the meta-system inside it

"The reflective layer" is the class SOURCE TEXT plus the meta-system that parses it. It is what lets the system show and rewrite its own code — inspectors read class member maps, and a snapshot can carry class-scope source edits. It is not what makes the world go.

It is five steps, and the first three have a name of their own because a lazy part needs exactly those and nothing else:

Both promises are memoized, so a part load and a later inspector open share one fetch. When the layer loads — if ever — is the profile's sources axis:

sourcesBehaviourWho ships it
backgroundfetch it once the world is up, off the critical paththe historical default
lazyfetch on first demand — opening an inspector, or restoring a snapshot with class-level editsproduction (2.28 MB, 62.7% of the tree, that a normal visit never downloads)
nonenever; ship none of it. No inspectors; class-level edits in a snapshot are refused with one clear reportthe lean appliance

The compiler is not part of any of this, and ships everywhere. compileFGCode lives in a file that always loads, because runtime compilation is product behaviour rather than a dev affordance: FizzyPaint tools, spreadsheet formulas (including reloading a saved sheet), per-widget {"$src"} records and Fizzytiles' LiveCodeLang are all compiled from source strings while the world runs. A compiler-less artifact is a non-interactive kiosk.

5 · Loading a part on demand

A part marked "eager": false is simply not in the booted page: the boot batch loader skips it, and on a precompiled tree its classes are absent from the image too. world.parts (PartsRegistry) is what brings one in later.

Two constraints the boot path does not have, both handled in _ingestPartPromise: findLoadOrder() scans every source the vault holds and is meant to run once before anything is defined, so the registry takes its order and keeps only the names this part just added; and a name that is already defined must not be re-ingested, because new Class would redefine a live class underneath running instances.

6 · Four questions, four different methods

This is the part most worth getting right, because a class-existence check answers none of these questions correctly for a lazy part: an undefined class means both "this artifact never shipped it" and "nobody has fetched it yet", and those two want opposite responses — do nothing, versus go and get it.

You want to know…AskNotes
Did this artifact ship the part at all?isAvailable name public; a lean build genuinely has no inspectors and there is nothing to open
Is it here yet?_isLoaded name private — whenAllLoaded is its only caller. A door that asks this itself is re-deriving the fast-path rule below
Run this once the parts are in — they are REQUIREDwhenAllLoaded [names], -> … rejects on a part this build never shipped. Right when the part constitutes the result
Run this once the parts are in — they are OPTIONALwhenOptionalPartsLoaded [names], -> … loads what is here, runs the callback regardless. Right when the part merely enriches the result
Construct a class core is not allowed to namelaunch "TheClass" names it as DATA — new (window[className]), the edge gate's sanctioned blind spot
Which parts does this snapshot need?partsNeededFor [classNames] reads the build MANIFEST, never the SourceVault — the vault only knows sources already loaded, so for a lazy part it cannot answer before the load, which is exactly when it is asked

Required or optional is a real decision, and getting it wrong is silent

A Sample*App document builds plots: without them it is broken, not reduced, so whenAllLoaded is right and rejecting loudly is the correct outcome. A window that merely offers a part's tools in a docked palette is fine without them — the toolbars already filter their own contents by class existence — so whenOptionalPartsLoaded is right there. Using the wrong one is invisible until a profile actually drops the part: DashboardsApp and SimpleSlideApp are core classes whose desktop icons always ship, and with whenAllLoaded their icons on a lean tree could only reject — no window, ever.

7 · Three traps peculiar to lazy parts

1 · An awaiting door must keep its already-loaded path SYNCHRONOUS. On every build the SystemTest suite runs, parts are eager and long since present — so going through .then anyway defers the effect by a microtask, which moves it a whole world cycle later, and the suite measures cycles. That is why whenAllLoaded exists as one method that runs its callback inline when the parts are already in, rather than as a conditional copied into every door. One rule in two places is how an earlier arc produced four bugs of one shape.

2 · Not every call site CAN await. An app is the easy case: launch is fire-and-forget, invoked by reflection with its result ignored. A creator button is not — both the click and the drag path consume createWidgetToBeHandled()'s return value synchronously, so there is no seam to defer through. The resolution is partition, not cleverness: put the button in the part it creates from, and its mere existence proves the part is loaded. Likewise, if every item of a palette belongs to one part, move the palette and its opener in too — filtering its contents would pop an empty window.

3 · ⭐ An icon is not its app. createDesktop places every desktop and Examples icon at boot, which looks like it forces each lazy app to keep a tiny eager sliver beside it purely so there is a class to construct. It does not. That construction only ever asked the app for a title and an icon, and the art is core — so the launcher holds appClassName as a string and, on the click, asks PartsRegistry which part owns that name, fetches it, and only then constructs and launches. All three launcher parts were deleted. What forces eagerness is boot-time reachability, and reading a name is not reaching a class. Two consequences: the boot site asks world.parts.canEverProvideClass rather than if SpreadsheetApp? — for a lazy class an existence test reads "not fetched yet" and would drop the icon for ever, whereas the question at boot is "can this artifact EVER produce it", so a profile that ships neither the door nor its app simply draws no icon; and a profile must still name a door's part and its app's part together, which buildProfile.py now checks by reading every shipped class's requiredParts instead of anyone remembering it.

4 · A folder is a door, and that is a third moment. Desktop icons are drawn at boot; a folder's contents are not drawn until it is opened, and bringUpTarget is fire-and-forget, so it can await. So the Examples folder fills itself on first open, buying a tier the desktop cannot have — the art only that folder draws stays out of the boot image entirely. At boot: the folder, empty; no icon, no art, no app class. On open: examples-icons, and the five openers are built — still no app. On click: that one app's part, and no other's, which is why the five doors are five ONE-CLASS parts (the part is the loading unit, so five in one part would mean opening any of them fetched all five). ⚠ Only art nothing else draws can move: the folder's other icons are drawn by desktop icons and by FolderWindowWdgt/BinOpenerWdgt at boot, so they are core whatever the folder does.

A saved world that names a lazy part's classes

Handled, and worth knowing about before relying on it: loadWorldSnapshot pre-scans the file's class names and loads the parts they need before touching the world — so a rejected part load leaves the old world standing rather than half-destroyed. On a profile that dropped the part outright the load is refused with a clear report, which is the accepted behaviour under the no-serialization-compat policy.

8 · What proves any of this still works

Since the suite can never observe laziness (§1), the coverage lives in Node rigs:

RigWhat it proves
parts-lazy-load-headless.js boots index.html, asserts the part is genuinely absent, drives the launcher, and waits for the pane's FIRST FRAME before reading pixels
parts-snapshot-load-headless.js round-trips a snapshot CONTAINING a lazy part's widgets — the only path that exercises the pre-scan; also that a rejected load leaves the old world standing
smoke-boot-headless.js --production the only gate on a production tree: booted from the image, no SWCanvas payload, a snapshot round-trip, nothing fetched at boot — and it loads every lazy part, asserting each was absent at boot, that all its classes arrive, and that ZERO eager batches came with it

Why that last one runs before the inspector probe, deliberately. Opening an inspector awaits the whole reflective layer, which pulls the meta-system in on its way past — and would therefore mask a completely broken part load. This ordering exists because the bug it now catches actually shipped: a lazy part on a precompiled tree died with findLoadOrder is not defined while every gate stayed green, because the only lazy part until then did not ship in production and every dev rig ran compile-at-boot, where the meta-system is present anyway. A capability's first use on a given artifact shape is untested by construction, however well the mechanism is covered elsewhere.
