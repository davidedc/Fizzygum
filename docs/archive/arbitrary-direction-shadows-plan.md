## §0 Orientation

Fizzygum shadows are ONE unified mechanism (`src/basic-widgets/Widget.coffee`, comment block "How the shadow painting works", ~:2793): a widget with `@shadowInfo` (an IMMUTABLE value object: `offset` Point + `alpha`, `keptByReferenceOnDeepCopy`, `src/ShadowInfo.coffee`) re-paints its WHOLE subtree once more, faintly and offset, BEHIND the normal paint — never baked into a back buffer, never a child widget. The shadow-pass paint contract: a shadow is the caster's per-pixel COVERAGE, chroma always black (the 2026-08-02/03 arcs; pinned by `SystemTest_macroTiltedFigureShadowAsDarkAsStraight` and `macroColoredCastersShadowNeutralBlack`).

The shadow-reach arc (closed 2026-08-10/11) made the DAMAGE side exact and direction-agnostic: `Widget.shadowExtendedRect(aRect)` = `(aRect ∪ aRect.translateBy(offset)).expandBy(1)`, applied in the widget's own plane BEFORE `mapRectToScreen` at the painted-footprint record, the island stash, and both flesh-out destination lanes. **Damage needs NO work in this plan.** The same arc moved every pixel READ onto the end-of-cycle seam (`MacroToolkit.captureAtEndOfCycle`) — the diff-oracle test patterns this plan reuses are catalogued in `src/macros/MACRO-PATTERNS.md` ("Staleness diff-oracles").

**Critical reframe from this plan's fact-finding:** the core shadow paint pass is ALREADY direction-agnostic in its design — it is two vector operations (translate the culling rect by −offset, translate the ctx by +offset). The remaining directional problems are not architecture, they are three localized defects: a LATENT ASYMMETRY BUG (two call sites pass two arguments to a one-parameter method, silently degrading the culling translate to a scalar), a sign bug in `fullImage`'s canvas sizing, and a dead parameter. Fixing them makes the code MORE uniform, not more general-purpose-complex.

## §2 The defects (all latent — zero reachable producers — which is exactly the point)

- **D1 — asymmetric-offset mis-cull (any sign):** the two-argument `translateBy` at the TWO `_fullPaintIntoAreaOrBlitFromBackBufferJustShadow` sites degrades the culling translate to a scalar of the x component. An offset like (12,4) culls the shadow pass as if it were (12,12): the incremental shadow render can drop or over-include band(s) relative to a full repaint — precisely the staleness class the diff oracle measures.
- **D2 — negative-offset `fullImage` clipping:** `bounds.growBy offset` with any negative component SHRINKS the image canvas; the widget's own pixels (and the shadow) get clipped out of the produced image. `fullImage` feeds offscreen imaging (e.g. drag ghosts/thumbnails — grep its callers at execution time).
- **D3 — dead `color` parameter** on `PopUpWdgt.addShadow` — an un-wired API affordance that misleads (the contract deliberately reserves colour for a future explicit ShadowInfo field).

## §3 The distilled argument

- **The fix is subtraction, not addition.** D1's fix replaces a broken two-arg call with `translateBy appliedShadow.offset.neg()` — fewer tokens, actually correct. D2's fix is the SAME union concept the damage side already uses (`bounds.merge bounds.translateBy offset`) — one concept reused instead of two grow disciplines. D3 is a deletion. Nothing gains a flag, a branch, or a mode; the mechanism becomes uniformly vector-typed. This is the owner's point 1 made concrete.
- **Latent ≠ harmless.** D1 already bites any asymmetric offset either sign — the first product feature to want a (2,6) shadow inherits a staleness bug with no breadcrumb. Closing it now, with tests, is cheaper than the future debugging session.
- **The slide principle needs the floor, not the UI, first.** Making direction unconditional at the mechanism level is the prerequisite for ever exposing shadows as user styling (§8); doing it while the shadow-reach context is fresh (probes, test patterns, and the union idiom all in place) minimizes cost.

## §6 Rejected alternatives (do not re-attempt blind)

- **Clamp/validate offsets to positive in `__addShadow`:** rejected in the shadow-reach arc already (contract clamps ban the mechanism from serving design) and doubly rejected by the slide principle — the whole point is that direction is a styling degree of freedom.
- **Bake per-widget/per-glyph shadows into back buffers:** the unified mechanism's founding ban ("a widget NEVER bakes its own shadow"; the per-glyph route is explicitly retired in the paint-contract comment). Direction support must ride the one recursive pass.
- **A directional variant of the damage union:** unnecessary — `shadowExtendedRect` is ALREADY direction-agnostic (the union covers any translate). Damage is done; only paint/imaging lag.
- **Wiring the `color` param instead of deleting it:** a coloured shadow is a real future feature but its home is an explicit `ShadowInfo` field with paint-contract design (how does "chroma always black" generalize?) — a dangling parameter on one pop-up class is the wrong seam. Delete now; design later if wanted (§8).
